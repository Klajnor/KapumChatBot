# 🤖 Telegram AI Bot — Qwen (Model Studio) + SQLite

Telegram-бот с интеграцией **Qwen** через OpenAI-совместимый API Alibaba Cloud
Model Studio. Поддерживает текстовые диалоги, распознавание голосовых сообщений,
анализ изображений, генерацию картинок, ответы в Markdown-разметке, выбор модели,
настройку системного промпта, гостевой доступ и **guest chat mode** — вызов бота
в любом чате или группе без добавления его туда.

## ✨ Возможности

- 💬 **Чат с AI** — модели Qwen 3.8 / 3.7 и DeepSeek V4 (список настраивается в `.env`)
- 📝 **Ответы в Markdown** — жирный/курсив, код, списки, ссылки, цитаты
  (MarkdownV2 с автоматическим fallback на HTML и plain text)
- 🧱 **Rich-сообщения (Bot API 10.1+)** — ответы приходят нативными «богатыми»
  сообщениями: GitHub-Flavored Markdown модели (таблицы `|…|`, формулы `$$LaTeX$$`,
  заголовки, списки, сноски) отображает сам Telegram — без Telegraph и PNG.
  При `STREAM_RESPONSES=true` в личке ответ печатается анимируемым
  rich-черновиком. `RICH_MESSAGES=false` или отказ Telegram → старый путь.
- 🧪 **Формулы (legacy-путь)** — без rich-сообщений блочные `\[...\]` и `$$...$$`
  отрисовываются локально в PNG, текст и картинки идут по порядку; короткие
  формулы переводятся в Unicode: `H_2SO_4` → H₂SO₄, `$E = mc^2$` → E = mc²,
  `\alpha` → α, `10^{23}` → 10²³ (блоки кода и `snake_case` не затрагиваются).
  При ошибке отрисовки или отправки используется текстовый вариант.
- 🌊 **Стриминг ответов** — ответ появляется кусками: в личке это анимируемый
  rich-черновик, в группах — сообщение, обновляемое раз в `STREAM_EDIT_INTERVAL`
  секунд; при любой ошибке стрима запрос автоматически повторяется одним
  вызовом (работает и для фото; гостевые ответы — нет: там ровно один результат)
- 📄 **Telegraph (fallback)** — ответы с таблицами/LaTeX, которые не удалось
  отдать rich-сообщением (или при `RICH_MESSAGES=false`), публикуются страницей
  Telegraph, а в чат приходит ссылка
- 🔀 **Спросить у другой модели** — под каждым ответом в личном чате кнопка
  повторить последний вопрос в другой модели (в группах и гостях не появляется)
- ⏳ **Индикатор ожидания** — если модель отвечает дольше 5 с, бот показывает
  сообщение «жду ответа» и обновляет его раз в секунду, а перед ответом удаляет
- ⏱️ **Время ответа API** — в конце сообщения: `⏱️ 2.3 с · qwen3.8-flash`
- 🛡️ **Ответ не теряется** — ретраи на лимитах Telegram (429), цепочка
  MarkdownV2 → HTML → plain, троттлинг ~1 сообщение/сек на чат и глобальный
  обработчик ошибок: вместо тишины пользователь получает сообщение
- 🎤 **Голосовые сообщения** — бот распознаёт речь (`qwen-audio-3.0-realtime-plus`,
  WebSocket Realtime ASR) и отвечает на распознанный текст как на обычный вопрос
- 🖼️ **Анализ изображений** — фото обрабатывают vision-модели (отмечены 🖼️ в `/models`)
- 🔧 **Обработка и улучшение фото** — «улучши», «увеличь разрешение», «убери шум»,
  «резкость», «реставрировать старое фото» — качество правится локально (Pillow),
  контент остаётся прежним; нейросеть только определяет намерение и подбирает операции
- 🎨 **Генерация картинок** — `/image <промпт>` или просто попросите «нарисуй…» —
  AI сам решит ответить текстом или картинкой
- 🩹 **Генерация стикеров** — `/sticker <промпт>` или попросите «сделай стикер…» —
  rembg удаляет фон, объект целиком вписывается в прозрачный WebP 512×512;
  кнопка под результатом позволяет создать набор или добавить стикер в ранее созданный
- 🔎 **Актуальный список моделей** — при запуске проверяется через `GET /models`; недоступные для аккаунта модели скрываются
- 🤖 **Выбор модели** — переключение модели командой `/models`
- ⚙️ **Системный промпт** — настройка поведения AI
- 📚 **История диалога** — контекст сохраняется в базе данных (SQLite) **по чату и пользователю**; участники группы не получают контекст друг друга
- 🧹 **Очистка истории** — сброс контекста текущего чата (`/clear`)
- 👥 **Группы** — бот отвечает на упоминание `@username` или на reply
- 🌍 **Guest chat mode** — `@bot вопрос` в **любом** чате или группе, даже там,
  где бот не состоит (Bot API 10.0, без inline-режима). Доступно чтение
  «второго мозга» (MCP), если он подключён. Если в истории уже был
  недоверенный документ/страница, следующая чистая просьба тоже не получает
  image-инструмент.
- 🎁 **Гостевой доступ** — неавторизованные пользователи получают несколько
  бесплатных вопросов; отклонённые запросы (слишком длинный текст, большое
  голосовое, сбой распознавания/генерации) квоту не расходуют
- 👑 **Администрирование** — белый список пользователей, дневной лимит и
  статистика за 14 дней
- 🛠 **Уровни доступа и меню `/admin`** — гость → пользователь → админ →
  владелец (`OWNER_IDS`). В меню-клавиатуре админ открывает карточку
  пользователя: персональный лимит запросов (±1/±5, ввод числа, сброс к
  `DAILY_LIMIT`), сброс сегодняшнего расхода, смена модели, сброс промпта,
  выдача/отзыв доступа, блокировка. Назначать и снимать админов может только
  владелец; заблокированные не получают ответов, даже как гости. Любая кнопка
  ♻️ сброса на значение по умолчанию (лимит, промпт, настройки дайджеста)
  срабатывает только после ввода слова `CONFIRM` (с учётом регистра)
- 📏 **Лимиты загрузки** — до 20 МБ на фото, до 50 МБ на альбом; бот
  предупреждает при превышении и не тратит квоту
- 🔤 **Английский интерфейс** — все сообщения, включая тематические отказы
  (Star Wars / Hitchhiker's Guide) и таймауты, переведены на английский;
  дефолтные промпты модели — на русском (бот по умолчанию отвечает по-русски)
- 📋 **Пагинация `/list_users`** — по 15 пользователей на странице,
  `/list_users 2` для перехода; рядом с ID показывается имя и `@username`
- 🧹 **Автоочистка альбомов** — фоновый сборщик удаляет несобранные
  media-group записи, предотвращая утечку памяти
- 🔒 **Лимит системного промпта** — 2048 символов через `/prompt`
  (настраивается: `MAX_SYSTEM_PROMPT_LENGTH`), превышение отклоняется
- ✏️ **Правка сообщений** — если пользователь отредактировал свой вопрос, бот
  сообщает, что ответ был на прежнюю версию, и предлагает спросить заново
  (квоту правка не расходует)
- 📣 **Broadcast** — `/broadcast <текст>` рассылает объявление всем
  зарегистрированным пользователям после подтверждения
- ❤️ **Health endpoint** — опциональный `GET /health` для systemd/Docker/uptime
  мониторинга (`HEALTH_PORT`, по умолчанию выключен)
- 📏 **Лимит текста в guest-режиме** — `MAX_GUEST_TEXT_LENGTH` (по умолчанию
  4000 символов)
- 🔢 **Счётчики токенов** — в футере ответа: время, модель и токены
  `↑input ↓output` (`TIMING_FORMAT_TOKENS`)
- ↩️ **Ответ по reply** — вопрос с ответом на чужое сообщение цитирует его
  текст для AI; reply на фото анализирует процитированное изображение;
  пересланные сообщения получают метку источника
- 📄 **Анализ документов** — загрузите PDF, DOCX, XLSX, PPTX или текстовый файл/код:
  текст извлекается (pdfplumber / python-docx / openpyxl / python-pptx) и разбирается моделью вместе
  с вопросом; сканы PDF (без текстового слоя) распознаются vision-моделью —
  OCR первых `PDF_OCR_MAX_PAGES` страниц
- 📹 **YouTube-суммаризация** — ссылка на видео (watch / shorts / live /
  youtu.be) заменяется субтитрами с таймкодами раз в минуту (`yt-dlp`), модель
  делает выжимку; видео без субтитров не распознаются на слух
- 🔗 **Анализ ссылок** — сообщение-ссылка загружается (SSRF-защита: только
  публичные хосты), основной контент страницы (trafilatura, fallback —
  встроенный парсер) добавляется в запрос к AI
- 🔎 **Веб-поиск (RAG)** — модель сама вызывает инструмент `search_web`, когда
  вопрос требует актуальных данных (новости, цены, свежие релизы); результаты
  возвращаются пронумерованными, ответ цитирует их как `[n]`. Провайдер по
  умолчанию — **DuckDuckGo** (пакет `ddgs`, **без API-ключа**); также
  поддерживаются Tavily / Brave / Exa (`SEARCH_API_KEY`). До
  `MAX_SEARCH_ROUNDS` итераций поиска на вопрос
- 🩺 **Свободный статус** — «как дела» или «статус» (намерение подтверждает
  короткий AI-запрос) показывает uptime, модель, доступность БД, остаток
  дневной квоты/пробных сообщений, счётчики второго мозга (заметки, фрагменты,
  проиндексированные и ожидающие связи) и живую проверку поиска. Проверка
  поиска — настоящий запрос к провайдеру не чаще `STATUS_SEARCH_INTERVAL`
  (по умолчанию раз в час на пользователя); при исчерпании лимита бот пишет
  время следующей проверки и не считает это ошибкой. Статус не расходует квоту
  вопросов, не пишет историю и в группах не показывает личные лимиты
- 🧰 **samo_helper (Redmine ↔ YouGile)** — отдельный рабочий модуль: уведомления Redmine в группу, карточки YouGile по `/samo_add`, поиск по саммари и ключевым словам `/samo_find` с исходными ссылками, личные напоминания. Включается `SAMO_HELPER_ENABLED=true`; не меняет БД диалогов. Инструкция — в разделе «samo_helper: Redmine ↔ YouGile».
- 🧠 **MCP и «второй мозг» в Obsidian** — админ подключает MCP-сервер `brain`,
  и модель сама ищет и читает личные заметки через `search_notes` / `get_chunk`
  / `get_note` / `list_notes`; чтение доступно всем пользователям диалога.
  Владелец в личке сохраняет заметки просьбой «запомни», выбором после форварда
  или кнопкой **🧠 Remember** под ответом. Диагностика `/mcp` — только владельцу
- ⏰ **Напоминания и регулярные сообщения** — `/remind in 30 minutes …`,
  `/remind daily at 9:00 …`, `/remind every 2 hours …`; префикс `ai:`
  превращает напоминание в регулярный запрос к модели (доставляется ответ);
  напоминания можно ставить и **свободным текстом** в чате («напомни завтра
  в 5 позвонить маме») — один лёгкий AI-вызов превращает фразу в обычное
  напоминание (`REMINDER_FREEFORM`);
  у каждого пользователя **своя таймзона** (`/timezone Europe/Moscow` или
  диалог `/timezone`, где AI угадывает зону и бот подтверждает совпадение
  часов); без неё действует `REMINDER_TIMEZONE`;
  лимиты: 10 разовых + 10 регулярных, регулярные не чаще раза в 30 минут
  (`/reminders` — список с кнопками ⏸ Пауза / ▶️ Продолжить / 🗑 Удалить и «Удалить все» с подтверждением; кнопки доступны только владельцу списка; `/delreminder N|all` тоже работает)
- 🎭 **Личности (personas)** — `/persona` выбирает готовую роль (Assistant,
  Programmer, Writer, Scientist, Teacher, Translator, Critic, Friend): это
  пресет системного промпта, переключаемый в один тап; активная личность
  видна в `/settings`. Свой каталог — через `PERSONAS` (JSON) в `.env`;
  полностью ручной промпт по-прежнему задаётся `/prompt`
- 📤 **Экспорт истории** — `/export [md|pdf]` сохраняет диалог файлом, а под
  каждым ответом в личке кнопки **📄 PDF** и **📝 MD** выгружают один ответ
  (вместе с вопросом). PDF рендерится локально (fpdf2 + шрифты DejaVu из
  matplotlib — кириллица работает) с вёрсткой Markdown: заголовки, списки,
  цитаты, блоки кода, таблицы (шапка, зебра, выравнивание колонок), формулы
  (display — картинками, простые инлайн — Unicode), ссылки, номера страниц; без fpdf2 автоматически отдаётся
  Markdown. Экспорт не тратит дневную квоту

## 🛠️ Стек технологий

- **Python 3.12+**
- **ffmpeg** — конвертация голосовых сообщений (OGG/Opus → PCM16) для ASR
- **aiogram 3.x (≥ 3.29)** — асинхронный фреймворк для Telegram Bot API
  (Bot API 10.1+: rich-сообщения, черновики, guest mode; 10.3 — в 3.31)
- **SQLite** — единственная поддерживаемая СУБД (файл в каталоге данных)
- **SQLAlchemy 2.0 (async)** + **aiosqlite** — ORM и драйвер
- **aiohttp** — HTTP-клиент
- **Qwen API** (Alibaba Cloud Model Studio, OpenAI-совместимый режим)

## 🚀 Установка и запуск

### 1. Клонировать репозиторий

```bash
git clone <repo-url>
cd ChatBot
```

### 2. Установить зависимости

```bash
python -m venv .venv
.venv\Scripts\activate        # Windows
# source .venv/bin/activate   # Linux/macOS
pip install -r requirements.txt
```

### 2a. Установить ffmpeg (для голосовых сообщений)

Telegram присылает голосовые как **OGG/Opus**, а Realtime ASR принимает
**PCM16 16 кГц**. Конвертацию делает `ffmpeg` — без него бот работает, но
голосовые сообщения не распознаются (в лог при старте попадёт предупреждение
`ffmpeg not found on PATH`).

**Windows** (любой из способов):

```powershell
winget install Gyan.FFmpeg          # winget (Windows 10/11)
# или
choco install ffmpeg                # Chocolatey
# или
scoop install ffmpeg                # Scoop
```

Если менеджера пакетов нет — скачайте сборку с
[ffmpeg.org/download.html](https://ffmpeg.org/download.html) (Windows builds),
распакуйте, например, в `C:\ffmpeg`, и добавьте `C:\ffmpeg\bin` в `PATH`
(Параметры → Система → О системе → Дополнительные параметры системы →
Переменные среды → `Path` → Изменить → Создать). Затем **перезапустите**
терминал.

**macOS**:

```bash
brew install ffmpeg
```

**Debian / Ubuntu**:

```bash
sudo apt update && sudo apt install -y ffmpeg
```

**Fedora / RHEL**:

```bash
sudo dnf install -y ffmpeg
```

**Docker** (в образ на базе Debian/Ubuntu):

```dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends ffmpeg \
    && rm -rf /var/lib/apt/lists/*
```

Проверка после установки:

```bash
ffmpeg -version
```

Команда должна напечатать версию, а не «command not found». Бот ищет `ffmpeg`
в `PATH`, поэтому отдельная настройка пути в `.env` не нужна. Если голосовые
не нужны вовсе — поставьте `ENABLE_VOICE=false`.

### 3. Настроить базу данных

Сейчас поддерживается **только SQLite** — отдельный сервер не нужен. Файл базы
создаётся в каталоге данных при первом запуске (`init_db`): в `.env.example`
это абсолютный `/var/lib/kapum-chatbot/chat_bot.db`. Все пути в конфигурации
**обязаны быть абсолютными** — относительные отклоняются при старте, потому что
код сервиса доступен только для чтения.

PostgreSQL и другие СУБД — **возможное будущее направление**, а не текущая
возможность: код местами сохраняет исторический задел (URL-диалекты, `asyncpg`
в requirements), но такая конфигурация не поддерживается и не тестируется.
Миграционного скрипта в репозитории нет; при возврате к PostgreSQL его нужно
будет писать заново вместе с тестами на все таблицы.

### 4. Настроить переменные окружения

Скопируйте `.env.example` в платформенный файл и заполните:

```bash
cp .env.example .env.linux     # Linux-сервер
copy .env.example .env.windows # Windows (тесты/локальный запуск)
```

`bot/config.py` читает **`.env.linux` на Linux** и **`.env.windows` на Windows**;
если платформенного файла нет, используется старый `.env` как fallback.
Все три файла с секретами исключены из Git. Переменные, уже заданные в
окружении (systemd `Environment=`), имеют приоритет.

| Переменная | Описание |
|-----------|----------|
| `BOT_TOKEN` | Токен бота от [@BotFather](https://t.me/BotFather) |
| `BOT_USERNAME` | Имя бота без `@` (необязательно — определяется при запуске) |
| `AI_API_KEY` | API-ключ Qwen / Model Studio (алиасы: `QWEN_API_KEY`, `DASHSCOPE_API_KEY`) |
| `AI_BASE_URL` | OpenAI-совместимый endpoint (см. ниже) |
| `MODEL_1_*` … `MODEL_6_*` | Шесть наборов настроек моделей для меню `/models` (см. раздел «Модели») |
| `FALLBACK_MODEL_*` | Седьмой набор — аварийная модель, если не ответила ни одна из шести (не показывается в меню) |
| `DATABASE_URL` | База данных: `sqlite+aiosqlite:////var/lib/kapum-chatbot/chat_bot.db` (абсолютный путь). PostgreSQL/другие СУБД — только будущее направление, сейчас не поддерживаются |
| `DEFAULT_MODEL` | Внутренний id модели по умолчанию (для новых пользователей и если для выбранной модели нет настроек) |
| `DEFAULT_SYSTEM_PROMPT` | Системный промпт по умолчанию (русский, с инструкцией отвечать по-русски) |
| `PERSONAS` | JSON-каталог личностей `/persona`: дополнение/замена встроенных (ключ → строка-промпт или `{"name","prompt"}`); пусто — только встроенные |
| `DEFAULT_TEMPERATURE` | Температура для новых пользователей |
| `DEFAULT_MAX_TOKENS` | Лимит токенов ответа для всех пользователей; применяется после перезапуска |
| `THINKING_LEVEL` | Уровень размышления публичных ответов: `off`, `low`, `medium`, `high`, `max` (по умолчанию `medium`); владелец меняет в `/admin → 🧠 Thinking` |
| `THINKING_BUDGET` | Точный лимит thinking-токенов, `0…262144` (по умолчанию `0` — использовать уровень); положительное значение переопределяет уровень |

### 5. Настроить endpoint Qwen

Используйте OpenAI-совместимый адрес Model Studio. Ключ должен быть создан в
**том же регионе**, что и URL:

| Регион | `AI_BASE_URL` |
|--------|----------------|
| Международный (Singapore) | `https://dashscope-intl.aliyuncs.com/compatible-mode/v1` |
| Китай (Beijing) | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| Workspace (рекомендуется) | `https://{WorkspaceId}.ap-southeast-1.maas.aliyuncs.com/compatible-mode/v1` |

### Модели

Модели для меню `/models` задаются **в `.env`** — код трогать не нужно.
Предусмотрено шесть наборов `MODEL_1_*` … `MODEL_6_*` и седьмой —
`FALLBACK_MODEL_*`. Поля набора:

| Поле | Назначение |
|------|------------|
| `NAME` | отображаемое имя (кнопка в меню, подпись «⏱️ … · модель») |
| `ID` | **внутренний** id бота: хранится как выбор пользователя, используется в кнопках; уникальный, провайдеру не отправляется |
| `URL` | URL провайдера (OpenAI-совместимый, `…/v1`); пусто — `AI_BASE_URL` |
| `MODEL` | id модели у провайдера (уходит в запрос как `model`) |
| `VISION` | `true` / `false` — принимает ли модель изображения |
| `API_KEY` | необязательно: ключ именно этого провайдера; пусто — `AI_API_KEY` |

```
MODEL_1_NAME=Qwen 3.8 Max
MODEL_1_ID=qwen3.8-max
MODEL_1_URL=https://dashscope-intl.aliyuncs.com/compatible-mode/v1
MODEL_1_MODEL=qwen3.8-max
MODEL_1_VISION=true
```

Набор без `ID` или `MODEL` пропускается (слот можно оставить пустым). Если не
заполнен ни один набор, используется встроенный `DEFAULT_AI_MODELS` из
`bot/config.py`. `AI_BASE_URL` / `AI_API_KEY` по-прежнему нужны для голоса и
генерации изображений.

**Модель по умолчанию.** `DEFAULT_MODEL` — внутренний id. Она выдаётся новым
пользователям, а также используется, если для сохранённого выбора пользователя
настроек нет (модель убрана из `.env` или изменён её `ID`). Пусто — первая
настроенная модель.

При запуске бот запрашивает `GET {URL}/models` у каждого провайдера и **скрывает**
из меню модели, которых нет в его списке (если запрос не удался — показывает
всё). Vision-модели помечаются значком 🖼️.

#### Автоматический fallback моделей

Если выбранная модель не ответила (ошибка API, пустой ответ) или ответила о
превышении квоты/лимита, бот повторяет запрос **следующей моделью по порядку
наборов**. Когда не ответила и последняя, запрос уходит в `FALLBACK_MODEL_*`.

- аварийная модель **не отображается** в `/models` и не может быть выбрана;
- для vision-запросов (включая стриминг фото и анализ альбома) перебираются только модели с `VISION=true`; если такой нет, изображение не отправляется;
- если не ответила ни одна модель, обычный чат показывает список фактических
  неудачных попыток: `модель — HTTP-код / код провайдера (описание); …`;
  учитываются streaming, обычные повторы и запросы без tools/thinking;
  одинаковые ошибки объединяются со счётчиком `×N`, длинный список разбивается
  на сообщения. Для таймаута/сети/невалидного или пустого ответа используются
  коды `TIMEOUT`, `NETWORK_ERROR`, `INVALID_RESPONSE`, `EMPTY_RESPONSE`
  (ошибка протокола потока — `STREAM_ERROR`). Ключи, токены и URL скрываются,
  текст описания ограничен; сырой JSON/HTML ответа не публикуется;
- в подписи «⏱️ … · модель» показывается та модель, которая реально ответила.

### 🧠 Размышления модели (thinking)

Одна общая настройка управляет «размышлением» всех ответов, которые видит
пользователь: обычный чат и стриминг, анализ фото и альбома, ответы гостя,
AI-напоминания и саммари каналов вместе с его модификатором промпта. Внутренние
запросы (определение intent, OCR, описания референсных картинок для генерации)
настройку не получают и работают с умолчаниями провайдера.

Две переменные `.env`:

| Переменная | Значение |
|---|---|
| `THINKING_LEVEL` | `off`, `low`, `medium`, `high`, `max` (по умолчанию `medium`) |
| `THINKING_BUDGET` | точный лимит thinking-токенов, `0…262144` (по умолчанию `0`) |

Владелец меняет оба значения в `/admin → 🧠 Thinking` — они хранятся в
`app_settings` и применяются без перезапуска; «Reset» возвращает значения из
`.env`.

Что уходит в API:

- `off` → `enable_thinking: false`;
- уровень без бюджета → `enable_thinking: true` + `reasoning_effort: <уровень>`;
- бюджет `> 0` → `enable_thinking: true` + `thinking_budget: N`, без
  `reasoning_effort` (Qwen 3.8 не принимает оба поля одновременно);
- `off` важнее бюджета.

Провайдер сам отображает уровень на свою шкалу: у Qwen 3.8 `low/medium/high/max`
превращаются в `low/medium/xhigh/xhigh`, у DeepSeek/GLM `low` и `medium`
отображаются в `high`. Если endpoint не понимает thinking-поля и отвечает
`400/422`, бот один раз повторяет запрос без них и запоминает модель до
перезапуска. У моделей, которые не умеют выключать thinking (например,
GLM-5.3), `off` фактически оставит thinking по умолчанию провайдера — в логе
будет предупреждение.

### Голосовые сообщения и картинки

- **Голос** → бот скачивает OGG/Opus, конвертирует его `ffmpeg`-ом в PCM16
  16 кГц и отправляет в `ASR_MODEL` (`qwen-audio-3.0-realtime-plus`) по
  **WebSocket** (Realtime API, Manual mode): `session.update` →
  `input_audio_buffer.append` (чанки по ~1 с) → `commit` → `session.finish` →
  `conversation.item.input_audio_transcription.completed`. Аудио — до 7,5 МБ
  исходного файла / 5 минут. Распознанный текст бот показывает сообщением
  «🎤 Recognized: …» **и сразу отправляет его нейросети как обычный вопрос** —
  дальше работает та же логика, что и для текстового сообщения (история,
  системный промпт, лимиты, стриминг, картинки). WebSocket-адрес выводится из
  `AI_BASE_URL`: `wss://{WorkspaceId}.ap-southeast-1.maas.aliyuncs.com/api-ws/v1/realtime`.
- **Картинки** → модель получает инструмент `generate_image` и сама решает,
  ответить текстом или сгенерировать изображение (например, «нарисуй кота»).
  Также доступна команда `/image <промпт>`.
- **Стикеры** → отдельный инструмент `generate_sticker` срабатывает, когда
  пользователь просит именно **стикер** («сделай стикер с котом»). Картинка
  генерируется с суффиксом «die-cut sticker style…», затем rembg удаляет фон,
  объект обрезается по альфа-каналу, целиком вписывается с отступами в
  прозрачный холст 512×512 и перекодируется в WebP ≤512 КБ —
  это настоящий Telegram-стикер (`answer_sticker`), который можно сохранить.
  Команда `/sticker <промпт>` делает то же явно. Отключается
  `ENABLE_STICKER_GENERATION=false`.

### Прозрачные стикеры и наборы

**Настоящая прозрачность.** Для непрозрачных исходников фон удаляет локальная
нейросеть **rembg / u2net** на CPU, без дополнительного платного API и без
отправки картинки стороннему сервису удаления фона. Нужные зависимости
`rembg[cpu]` и ONNX Runtime устанавливаются через `pip install -r requirements.txt`.
Нативная прозрачность исходника сохраняется без повторного удаления фона.
Модель выделяет основной объект, но может ошибаться на мелких деталях, надписях
и полупрозрачных элементах; нарисованные «шашечки» сами по себе прозрачностью не являются.

При первой обработке rembg скачивает модель u2net (около 176 МБ) и кэширует её
в каталог из `STICKER_MODEL_DIR` (по умолчанию в `.env.example` —
`/var/lib/kapum-chatbot/rembg`), а не в домашнем каталоге пользователя службы.
Путь **обязан быть абсолютным**: относительные значения отклоняются при старте,
чтобы модель не оказалась в root-owned каталоге кода. Каталог автоматически
создаётся перед загрузкой модели, веса не попадают в Git.

```dotenv
STICKER_MODEL_DIR=/var/lib/kapum-chatbot/rembg
```

Поддерживается `~`. Приоритет: `STICKER_MODEL_DIR` → явно заданный
`U2NET_HOME` → встроенное значение для разработки. Бот передаёт rembg
абсолютный путь через `U2NET_HOME`.
После изменения `.env` перезапустите бота. Существующая модель из старого кэша
не переносится автоматически: скопируйте `u2net.onnx` в выбранный каталог или
дождитесь повторного скачивания. Пользователь службы должен иметь доступ
на чтение/запись; при закрытом для записи каталоге задайте другой абсолютный путь.
Не требуется запускать бота от root или выдавать права `777`.

В комплектном `chat_bot.service` запасной `U2NET_HOME` указывает на
`/var/lib/kapum-chatbot/rembg`: systemd создаёт каталог с владельцем
`brain`, а `ProtectHome=true` не мешает загрузке. Если в `.env` задан
относительный `STICKER_MODEL_DIR`, сервис не запустится — замените его на
абсолютный `/var/lib/kapum-chatbot/rembg`.

Нужны доступ к сети, место на диске и дополнительная RAM для ONNX; GPU не требуется.
Сессию модель загружает один раз на процесс. Первый запуск заметно дольше;
при необходимости увеличьте `STICKER_PROCESSING_TIMEOUT` (по умолчанию 120 с,
максимум 600). Для предварительной загрузки от имени пользователя службы:

```bash
python -c "from bot.services.stickers import configure_model_cache; configure_model_cache(); from rembg import new_session; new_session('u2net', providers=['CPUExecutionProvider'])"
```

Удаление фона и WebP-кодирование работают в отдельном потоке, не блокируя бота.
Одновременно обрабатывается один стикер на процесс, очередь не накапливается.
Таймаут прекращает ожидание, но не убивает ONNX-поток: до его завершения новые
обработки отклоняются. При сбое/занятости/таймауте непрозрачная подмена не
отправляется, пользователь получает уведомление, списанная квота возвращается.
Время обработки включается в тайминг ответа.

**Если стикер не получился**, бот сообщает этап и конкретную доступную причину,
а не общий список возможных сбоев: отсутствие rembg/Pillow/ONNX Runtime,
ошибка загрузки CPU-runtime, загрузки модели или прав на кэш, нехватка памяти,
ошибка сегментации, пустой/непрозрачный результат, ошибка WebP или превышение
512 КБ. Отдельно показываются занятость процессора и таймаут с текущим лимитом
в секундах; бот подсказывает, что проверить или установить. Для генерации
различаются отсутствие HTTP-ответа (сеть/таймаут), HTTP 400/401/403/404/429/5xx,
пустой ответ, отсутствие URL и сбой скачивания исходника. Если нижележащий API
не сохранил более точные сведения, бот не выдумывает причину: точные ответы
провайдера и traceback с этапом обработки доступны администратору в журнале.
Пользователь получает только заранее заданные безопасные пояснения — без
сырых исключений, внутренних путей, URL с параметрами и ключей API.

**Добавление в набор:**
1. Отправьте `/sticker <описание>` или попросите стикер обычным сообщением.
2. В сообщении под отправленным стикером нажмите **«➕ Add to sticker set»**.
3. Выберите свой существующий набор из списка (есть страницы) либо
   **«➕ Create new set»**. Название нового набора формируется автоматически
   из имени пользователя с коротким уникальным суффиксом, техническое имя
   уникально, стикеру назначается 🙂.
4. Бот создаст набор через `createNewStickerSet` или добавит стикер через
   `addStickerToSet` и покажет **«Open sticker set»** — ссылку установки в Telegram.
   Кнопка **«Add to another set»** позволяет сохранить его ещё в один набор.

Список содержит только наборы, созданные этой функцией **этого бота для вас**.
Произвольные наборы (в том числе созданные через @Stickers или другим ботом)
подключить нельзя: Bot API разрешает боту изменять лишь созданные им наборы.
Старые наборы, созданные вне этой функции, автоматически не импортируются.
В группах кнопку может использовать только автор запроса; если Telegram
отказывает в создании, сначала откройте бота в личке и нажмите `/start`.
При заполненном/удалённом наборе или ограничении частоты бот сообщает об ошибке;
выберите другой набор, создайте новый либо повторите позже.

Операции с наборами **не расходуют квоту вопросов** и доступны авторизованному
пользователю даже с исчерпанной квотой; заблокированным доступ закрыт. Повторное
нажатие не дублирует стикер (проверяется Telegram `file_unique_id`); повторное
создание набора для того же стикера возвращает ранее созданный набор. Привязки
кнопок, владельцы и наборы сохраняются в БД и переживают перезапуск; байты
картинок в БД не хранятся. Новые таблицы создаются автоматически при запуске
(SQLite). `ENABLE_STICKER_GENERATION=false` отключает
также кнопки наборов.

### Фото: анализ, генерация и улучшение

**Фото: три сценария.** При входящем фото (или reply-вопросе к фото) бот сначала
делает лёгкий классифицирующий запрос к нейросети (одним словом, `temperature=0`)
и по ответу выбирает действие:

| Намерение | Пример подписи | Что делает бот |
|-----------|----------------|----------------|
| `analyze` | «что на фото?» | Vision-анализ (обычный путь) |
| `generate` | «нарисуй похожее», «измени стиль на киберпанк» | Vision описывает референс → генерация новой картинки по описанию и референс-изображению |
| `enhance` | «улучши фото», «увеличь разрешение», «убери шум», «реставрируй старое фото» | Улучшение **двумя способами** (см. ниже), операции подбирает классификатор (`enhance: upscale, sharpen`) |

**Бюджет классификатора.** Платная маршрутизация фото имеет отдельные лимиты:
20 попыток на пользователя и 200 на весь бот за UTC-сутки
(`PHOTO_INTENT_DAILY_LIMIT`, `PHOTO_INTENT_GLOBAL_DAILY_LIMIT`). Они действуют
для всех ролей, одиночных фото, альбомов и guest-mode. Оба счётчика атомарно
резервируются в БД до классификации и сохраняются после перезапуска. Попытка
не возвращается при ошибке модели, отказе text-only или незавершённом выборе
улучшения; квота обычных вопросов при этом сохраняет прежние правила возврата.
При исчерпании любого бюджета (или значении 0) классификатор пропускается:
применяется обычный анализ фото, без автоматической генерации/улучшения.
Фото без подписи не расходует этот бюджет. Это лимит попыток маршрутизации,
не денежный лимит всех AI-вызовов; внутренние retries/fallback модели и
бесплатные помощники напоминаний/часового пояса — отдельные механизмы.

**Пересланные и чужие фото.** Если фото переслано или это reply на фото
другого участника, изображение считается недоверенным: подпись и содержимое
оборачиваются в `<untrusted_content source="photo">`, а в сохранённой истории
остаётся метка происхождения (`[Forwarded image from …]` / `[Image from …]`).
Следующий вопрос по этому диалогу снова включает защитный режим: модели
добавляется правило про недоверенный текст, MCP-инструменты не предлагаются.
Своя подпись пользователя (reply-вопрос к чужому фото) остаётся вне рамки —
как «User request» у документов. По пересланной подписи классификатор
`generate`/`enhance` не запускается, чтобы чужие слова не включали платную
генерацию; выполняется обычный анализ. Защита снижает риск prompt injection,
но не делает распознавание изображения доверенным: ответ vision остаётся
ответом модели, а не проверенным фактом.

**Улучшение фото — два способа.** 🖥️ *Сервер*: локальная обработка Pillow
(`upscale` 2× до 4096 px, `denoise`, `sharpen`, `color`, `contrast`,
`brightness`, `restore`) — быстро, бесплатно, контент не меняется.
🧠 *Нейросеть*: фото перерисовывается моделью генерации с инструкцией
«сохрани всё как есть, подними качество» — возвращает утраченные детали
ценаю небольших изменений и одного запроса генерации.

**Выбор способа.** В **личном чате** бот сначала задаёт уточняющий вопрос
кнопками (🖥️ Server / 🧠 Neural network) — сам вопрос лимит не тратит, квота
списывается только после нажатия (callback `enh:local` / `enh:ai`, запрос
живёт 10 минут, фото скачивается по file_id заново). **В группах** — сразу
серверный путь без вопросов. **В гостевом режиме** доступен **только
нейросетевой** путь: гостевой ответ — единственный inline-результат, бот не
может загрузить в него файлы, поэтому улучшенное фото приходит ссылкой на
результат генерации. Если `ENABLE_IMAGE_GENERATION=false`, выбора нет —
всегда сервер (нейро-путь это вызов генерации).

Оба пути улучшения не требуют vision-модели: операции подобраны
классификатором, серверный путь работает на Pillow без платных вызовов,
нейросетевой — один вызов генерации. Неприменимые для конкретного файла
серверные операции отбрасываются (апскейл уже большого фото → дефолтный
конвейер), прозрачность PNG сохраняется, EXIF-поворот применяется. Несколько
фото в альбоме (media group) собираются за 1,5 с и обрабатываются вместе:
анализ — одним запросом со всеми картинками, генерация/улучшение — по каждому
фото; приватный альбом тоже сначала спрашивает способ. До первого скачивания
проверяется актуальная авторизация: заблокированный/неавторизованный
пользователь получает один отказ, байты не загружаются; в группе без
упоминания бота сбор вообще не начинается.

**Память альбомов.** Общий бюджет исходных байтов — 200 МиБ, не более восьми
альбомов одновременно и двух от одного пользователя, до десяти фото в альбоме.
До скачивания атомарно резервируются объявленный размер и возможная копия
буфера; при неизвестном размере резервируется `MAX_PHOTO_BYTES`. Ограничение
проверяется во время записи: заниженный `file_size` не позволяет выйти за
резерв, такой файл отклоняется. После загрузки резерв уменьшается до реального
размера. Готовые альбомы остаются в учёте до конца обработки; ошибки и отмена
освобождают резерв. Это консервативный лимит payload-буферов, не OS-лимит RSS:
сетевые чанки, декодированные изображения и память AI/Pillow в этот бюджет не входят.

Генерация использует нативный API DashScope
(`{AI_BASE_URL → /api/v1}/services/aigc/multimodal-generation/generation`),
результат скачивается и отправляется в чат. В guest-режиме картинка отдаётся
сразу ссылкой (`InlineQueryResultArticle`: подписанный URL нельзя передать как
inline-фото, и загрузить файл гостевой бот не может).

**Диагностика голосовых:** если бот отвечает «Could not recognize the voice
message»:

1. `ffmpeg -version` — команда должна печатать версию, а не «command not found»;
2. `ENABLE_VOICE=true` в `.env`;
3. модель из `ASR_MODEL` есть в выводе `GET {AI_BASE_URL}/models`;
4. для нестандартного региона задайте `ASR_WS_URL` явно, например
   `wss://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/api-ws/v1/realtime`.

Скачивание идёт **отдельной сессией без заголовка `Authorization`**: API
возвращает подписанную ссылку на Alibaba Cloud OSS, а такие URL отдают `403`,
если в запросе есть ещё и токен («only one auth mechanism allowed»). Сначала
идёт анонимный запрос; с токеном повторяется только если файл отдаёт сам API-хост
(ключ не уходит на сторонние хранилища). Ошибка логируется вместе с
телом ответа (подпись в лог не попадает). Если байты всё же не удалось получить,
бот просит Telegram скачать картинку по URL сам, а при неудаче отправляет
кликабельную ссылку (живёт ~24 часа) вместо сообщения об ошибке.

### Форматирование ответов (Markdown)

Ответы модели приходят в разметке. `PARSE_MODE` задаёт формат:

| Значение | Что делает |
|----------|-----------|
| `markdown` | MarkdownV2 (по умолчанию) |
| `html` | HTML-разметка Telegram |
| `plain` | текст без разметки |

С включённым `RICH_MESSAGES` (по умолчанию) этот раздел — про **fallback**:
rich-сообщение использует Markdown модели как есть и не зависит от `PARSE_MODE`.

Markdown модели (`**жирный**`, `*курсив*`, `` `код` ``, блоки кода, списки,
заголовки, ссылки, цитаты, `~~зачёркнутый~~`) преобразуется в корректный
MarkdownV2 с экранированием всех спецсимволов — `bot/services/markdown.py`.
`snake_case` и URL не ломаются. Длинные ответы режутся по границам блоков с
учётом уже отрендеренной длины.

Если Telegram всё же отклоняет разметку, сообщение автоматически
переотправляется как HTML, а затем как plain text — ответ не теряется.

### Формулы и научные обозначения

С `RICH_MESSAGES=true` (по умолчанию) LaTeX считается **нативно самим
Telegram**: `$…$`, `$$…$$` и ```math-блоки в rich-сообщении отображаются
формулами, поэтому текст до rich-пути не нормализуется вообще. Ниже — что
происходит на legacy-пути (`RICH_MESSAGES=false`, old-клиенты, отказ rich):

В обычной подписке **нет** рендеринга LaTeX и нет форматирования подстрочных/надстрочных
индексов (в MarkdownV2 и HTML нет `sub`/`sup`), а модели любят отвечать именно
так. Поэтому ответ прогоняется через `bot/services/science.py` и переводится в
Unicode-символы, которые выглядят одинаково на любом клиенте:

| Модель прислала | Пользователь видит |
|-----------------|--------------------|
| `H_2SO_4`, `CO_2`, `Ca(OH)_2` | H₂SO₄, CO₂, Ca(OH)₂ |
| `\ce{2H2 + O2 -> 2H2O}` | 2H₂ + O₂ → 2H₂O |
| `$E = mc^2$`, `m/s^2` | E = mc², m/s² |
| `6.022 \times 10^{23}` | 6.022 × 10²³ |
| `\frac{s}{t}`, `\sqrt{2}` | s/t, √2 |
| `\alpha`, `\Delta G`, `\Omega` | α, ΔG, Ω |
| `25 ^\circ C` | 25 °C |
| `\leq`, `\neq`, `\pm`, `\approx` | ≤, ≠, ±, ≈ |
| `A -> B`, `a <= b` | A → B, a ≤ b |
| `x_{max}`, `x_1`, `\vec{F}` | xₘₐₓ, x₁, F⃗ |

Что **не** меняется:

- содержимое блоков кода ` ``` ` и инлайн-кода `` ` ``;
- идентификаторы `user_name`, `MAX_VALUE`, `item_1`, `x86_64` (подстрочный
  индекс ставится только там, токен разбирается как последовательность
  химических элементов — используется таблица Менделеева);
- цены `$5 и $10`, пути `C:\Users\test`, неизвестные `\команды`.

Дополнительно модели через системный промпт объясняется, как форматовать ответ
(`ENABLE_STYLE_HINT`, текст — `STYLE_HINT`): по умолчанию промпт выбирается по
режиму доставки — для rich-сообщений разрешены таблицы и `$$LaTeX$$`, для
legacy-пути — Unicode и отказ от таблиц/LaTeX. Поэтому нормализация обычно лишь
подстраховка.

Ограничение Unicode: заглавных подстрочных букв не существует, поэтому `N_A`
(постоянная Авогадро) и `K_eq` остаются как есть, а символы вроде `ₓ ᵢ ₘ ₐ`
поддерживаются не всеми шрифтами. Если нужна настоящая математическая вёрстка,
формулу придётся отдавать картинкой (см. ниже «Что можно улучшить»).

Отключается целиком: `NORMALIZE_FORMULAS=false`.

### Индикатор ожидания («жду ответа»)

Запросы к модели (особенно с инструментами, анализом фото и генерацией картинок)
могут идти десятки секунд. Чтобы это не выглядело зависанием:

1. `PROGRESS_DELAY` секунд (по умолчанию 5) бот ждёт молча;
2. если ответ ещё не пришёл — отправляет сообщение
   `⠹ Жду ответа нейросети… 6 с`;
3. каждые `PROGRESS_INTERVAL` секунд (по умолчанию 1) **редактирует** его,
   обновляя спиннер и счётчик секунд, и параллельно освежает статус «печатает…»;
4. как только ответ готов — сообщение **удаляется**, и следом уходит сам ответ.

Если модель ответила быстрее порога, лишнее сообщение не появляется вообще.
Все вызовы Telegram здесь best-effort: ошибки отправки/редактирования/удаления
логируются и никогда не ломают ответ. Текст настраивается через `PROGRESS_TEXT`
(плейсхолдеры `{spinner}` и `{seconds}`), в группах сообщение отправляется как
reply на вопрос пользователя.

В guest chat mode индикатор не используется: там разрешён ровно один ответ
(`answerGuestQuery`), отдельное сообщение отправить нельзя.

### Время обработки запроса

Время, которое модель потратила на ответ, замеряется на стороне клиента
(`bot/services/ai_client.py`, вместе с `usage` — счётчиком токенов) и
добавляется в конец сообщения:

```
Ответ модели…

⏱️ 2.3 s · qwen3.8-flash · ↑1523 ↓487 tok
```

Формат задаётся в `TIMING_FORMAT` (`{seconds}`, `{model}`, `{tokens}`),
отключается — `SHOW_TIMING=false`. Когда API вернул счётчики токенов
(текстовые и vision-ответы), используется `TIMING_FORMAT_TOKENS` —
в нём дополнительно доступны `{input}` (prompt-токены) и `{output}`
(completion-токены); для картинок, где usage не сообщается, остаётся
обычный `TIMING_FORMAT`. Подпись добавляется только к тексту ответа:
в истории БД сохраняется чистый ответ без неё. Для картинок время генерации
попадает в подпись к фото, для голосовых — время распознавания в строку
«🎤 Recognized (1.2 с)», в guest chat mode — в текст ответа или в подпись
картинки. Если время неизвестно (например, 0), подпись не добавляется.

Замер делается вокруг самого HTTP-запроса к API (`_post_chat`), поэтому в число
не входит работа с базой и отправка в Telegram; при ретраях на 429/5xx
учитывается всё время с повторами.

### 📄 Анализ документов и 🔗 ссылок

**Документы.** Загруженный файл (в личке — любой, в группах — только когда
боту адресован) определяется по расширению/MIME: **PDF**, **DOCX**, **XLSX**, **PPTX** и плоский
текст/код (TXT, MD, CSV, JSON, PY, …). Текстовый слой извлекается
(`pdfplumber`, `python-docx`, `openpyxl`, `python-pptx` — опциональные
зависимости; таблицы DOCX превращаются в строки `a | b | c`. **XLSX**: каждый
лист — блок `## Sheet: имя` со строками `a | b | c` (до 20 листов и 5000
строк на лист, значения формул берутся из кэша файла). **PPTX**: блоки
`## Slide N` с текстом, таблицами и заметками докладчика. Старые `.xls`/`.ppt`
не поддерживаются), обрезается до `MAX_EXTRACTED_CHARS`
и уходит модели вместе с подписью-вопросом:

```
<untrusted_content source="document">
[Document: report.pdf]

<извлечённый текст>
</untrusted_content>

---

User request: <подпись файла или «Summarize this document…»>
```

Извлечённый текст сохраняется в историю, поэтому работают уточняющие вопросы
(«что во втором разделе?»). **Сканы PDF** (нет текстового слоя) не отклоняются: первые
`PDF_OCR_MAX_PAGES` страниц (по умолчанию 5, максимум 20) рендерятся в JPEG и
распознаются vision-моделью — по одному запросу на страницу (до 3
параллельно). Вызывается выбранная пользователем модель; если у неё
`VISION=false`, `model_chain` переходит к vision-модели и не отправляет ей
изображение. Каждая страница — платный вызов, поэтому лимит жёсткий; бот
сообщает, сколько страниц прочитано, а модель получает пометку «OCR,
возможны ошибки, остальные страницы не прочитаны». Нужна vision-модель в цепочке
моделей; отключается `ENABLE_PDF_OCR=false`. Ошибки
скачивания/извлечения и слишком большие файлы (> `MAX_DOCUMENT_BYTES`)
квоту не расходуют. Кодировки текста: BOM/UTF-16 → UTF-8 → cp1251/koi8-r →
latin-1.

**PDF Flate-лимиты.** При разборе через pdfminer распаковка ограничивается до
выделения полного результата: **8 МиБ на один Flate-поток/этап** и **64 МиБ
суммарно на документ** (включая цепочки фильтров и повреждённые потоки).
Превышение отклоняет PDF с возвратом квоты и без повторного OCR. Лимиты
фиксированы в коде; это не общий предел памяти PDF-парсера или PDFium:
другие декодеры требуют отдельных ограничений/изоляции; обход страниц ограничен
отдельно, как описано ниже.

**PDF-страницы.** Текстовый разбор создаёт не более 200 объектов страниц,
OCR — не более `PDF_OCR_MAX_PAGES`. Полный список страниц заранее не строится,
в том числе при очистке. Обход дерева ограничен 4096 узлами, глубиной 128 и
дедлайном; циклы и недостоверный `/Count` не вызывают полного перечисления.
Для обрезанного OCR точное общее число страниц остаётся неизвестным: бот
пишет, что прочитал первые N страниц и не читал оставшиеся. Для небольшого
полностью пройденного документа число точное. Нативная растеризация PDFium
по-прежнему требует отдельной процессной изоляции для жёсткого RAM-лимита.

**Недоверенный контент.** Текст документов, страниц, цитат/форвардов и
результатов поиска обрамляется тегами `<untrusted_content …>`; в системный
промпт добавляется правило считать его **данными, а не инструкциями**
(`bot/services/untrusted.py`). Если такой контент есть в текущем запросе *или
в истории*, MCP-инструменты («второй мозг») на этот запрос не предлагаются:
страница не должна уметь заставить модель прочитать личные заметки и передать
их наружу. По той же причине убираются платные и отправляющие инструменты —
`generate_image`, `generate_sticker` и `send_files`: чужой текст не может
инициировать генерацию или выгрузку файла. Маркеры сохраняются в истории,
поэтому уточняющие вопросы остаются защищёнными. Явный новый веб-поиск или
поиск по заметкам может выполняться отдельно от такой истории — см. разделы
«Веб-поиск» и «MCP-провайдер „Второй мозг“» ниже.

**Ссылки.** Если сообщение состоит практически из одних ссылок (свободного
текста ≤ 300 символов), бот загружает до 2 страниц и подставляет их контент
в запрос тем же форматом (`<untrusted_content source="web">` + `[Web page:
url]` + Title + текст). Длинные сообщения со ссылками не трогаются — это
обсуждение, а не просьба прочитать. Извлечение основного контента —
`trafilatura` (когда установлен), иначе встроенный stdlib-парсер
(скрипты/стили/навигация отбрасываются). PDF по ссылке разбирается как
документ. Результаты `search_web` оборачиваются тегом `source="search"`
аналогично.

**SSRF-защита** (`bot/services/documents.py`): fetch выполняется только после
проверки доступа (неавторизованные пользователи не могут заставить сервер
ходить в сеть); разрешены лишь `http(s)`-хосты, резолвящиеся в публичные IP —
loopback, частные сети и link-local (`169.254.169.254` — metadata облаков)
отклоняются; редиректы ведутся вручную с проверкой **каждого** хопта; размер
загрузки ограничен 5 МБ.

### 🔎 Веб-поиск (RAG)

Когда вопрос требует актуальных данных (новости, цены, свежие релизы, погода,
документация), модель сама вызывает инструмент `search_web` — бот выполняет
запрос к поисковому провайдеру, **читает первые 10 страниц выдачи** и возвращает
модели их текст с нумерацией. Она даёт **общее саммари по прочитанным источникам
с цитатами** `[n]` и ссылками, отмечая выводы и расхождения.
Если провайдер вернул меньше результатов, читаются все доступные.

**Дата:** обычный AI-чат и AI-напоминания получают текущую дату/время и явно
вычисленное «вчера» в системном промпте. Используется глобальный
`REMINDER_TIMEZONE` (по умолчанию UTC), а не даты из старой переписки.

**История и безопасность:** документ, страница, цитата/форвард, фото или
результат MCP в контексте отключают поиск, чтобы чужой текст не мог отправить
частные данные поисковому провайдеру. Результаты самого поиска допускают
уточнение запроса. Если недоверенные материалы остались **только в истории**,
любой новый самостоятельный запрос работает в изолированном режиме: в модель
идут системный промпт и текущий чистый запрос, без всей прежней переписки,
включая пересказы документов. Не требуется ни глагол «найди», ни слово
«интернет» — достаточно, чтобы сообщение было новым вопросом/просьбой, а не
уточнением по самому документу («объясни второй пункт»). Признаки нового
запроса и уточнения описаны в `bot/services/request_scope.py`. Из инструментов
доступен только поиск, без MCP, картинок, стикеров и файлов. История в БД не
удаляется. Явные просьбы к заметкам маршрутизируются в изолированный MCP-режим
(см. раздел о втором мозге): если в тексте есть оба указания, побеждает то,
которое стоит раньше — «найди **в интернете** плагины в Obsidian» остаётся
веб-поиском, а «найди **во втором мозге** заметки про поиск в интернете» —
заметками. Если в самом новом запросе есть внешний контент или это обычное
уточнение по документу, прежний запрет поиска сохраняется. То же правило
действует для AI-напоминаний.

**Текст вместо вызова:** JSON вида `{"name":"web_search","arguments":…}`
в обычном тексте ответа не исполняется. Если соответствующий инструмент был
предложен модели, он не считается итоговым ответом: бот делает один повтор
для этой модели с требованием штатного `tool_calls`, для поиска передаёт
`tool_choice=search_web`. Повторная имитация или отказ запускают обычную
fallback-цепочку. Если инструменты **не** предлагались (обычный чат, vision,
OCR, саммари), удаляется только сам JSON-объект, а остальной ответ сохраняется —
пример вызова в прозе больше не проваливает всю fallback-цепочку. Примеры
внутри блоков кода не затрагиваются. Потоковый предпросмотр придерживает
недостроенный JSON только когда инструменты предложены: обычный ответ с
`{"a": 1}` больше не «замирает» на первой `{`. Восстановление поддержанного
DSML-поиска также выполняется до очистки текста в обоих режимах.

```
User: «Что показали на WWDC 2026?»
  → tool_call: search_web("WWDC 2026 announcements")
  → бот: «🔎 Searching the web: WWDC 2026 announcements»
  → tool-ответ: [1] … URL, [2] … URL, [3] …
  → AI: итоговый ответ со ссылками [1][3]
```

**Провайдеры** (`SEARCH_PROVIDER`): `duckduckgo` (по умолчанию), `tavily`
(LLM-ориентированный API, https://tavily.com, ключи `tvly-…`), `brave`
(Brave Search API, токены `BSA…`) и `exa` (Exa Search API, https://exa.ai,
ключ из личного кабинета).

**DuckDuckGo работает без API-ключа и без регистрации** — нужен только пакет
`ddgs` (`pip install -r requirements.txt`). Он загружает HTML-страницу выдачи
`html.duckduckgo.com`, поэтому сайт может отвечать `202` (антибот-страница)
при частых запросах с одного IP: тогда поиск считается пустым, а бот честно
отвечает из своих знаний. `SEARCH_DDGS_BACKEND` задаёт движок внутри `ddgs`:
`duckduckgo` (по умолчанию — только выдача DuckDuckGo, быстро) либо `auto` /
список через запятую (`duckduckgo,bing`): источников больше, но библиотека
опрашивает их последовательно, и поиск может занять десятки секунд. Прокси
`ddgs` берёт из переменной окружения `DDGS_PROXY`. Без пакета `ddgs`
инструмент модели не предлагается (как и раньше).

**Tavily, Brave и Exa** — платные API: ключ задаётся в `SEARCH_API_KEY`; для
совместимости `TAVILY_API_KEY` читается только при `SEARCH_PROVIDER=tavily`
(после `SEARCH_API_KEY`), а `EXA_API_KEY` — только при `SEARCH_PROVIDER=exa`
и имеет приоритет над общим ключом; у Brave отдельного алиаса нет, только
`SEARCH_API_KEY`. Поэтому ключ одного провайдера не уйдёт на чужой хост.
**Без ключа эти провайдеры не включаются** — бот работает как раньше, полностью
обратно совместимо. `SEARCH_API_URL` позволяет указать свой endpoint
(например, прокси).

**Прямые вызовы без редиректов.** AI-клиент (`AI_BASE_URL`) и Telegraph API
вызываются с `allow_redirects=False`: 307/308 на другой host не повторяют тело
запроса с историей, файлами или `access_token`. Если настроенный endpoint
отвечает редиректом, в журнале будет явное предупреждение с именем клиента,
статусом и хостом — укажите конечный URL без редиректа. Уведомления
автообновления (`scripts/update_support.py`) идут в Telegram минуя прокси из
окружения, чтобы `BOT_TOKEN` в URL не попал в `HTTPS_PROXY`; на сетях, где
Telegram доступен только через прокси, прямая доставка завершится с понятной
записью в stderr (без токена и текста ошибки).

**Exa** запрашивается через `POST https://api.exa.ai/search` с заголовком
`x-api-key`; бот просит только `highlights` (сниппеты), а сами страницы, как и
у остальных провайдеров, читает через SSRF-защищённый `fetch_url_text`. Так
ответ Exa остаётся компактным, а полный текст страниц не обходит проверку
публичных адресов.

**Региональная блокировка Exa.** Exa по требованиям санкций блокирует API из
России, Украины, Крыма, Кубы, Ирана, Северной Кореи, Сирии и Венесуэлы.
Cloudflare отвечает HTML-страницей `403`/`Attention Required` ещё до проверки
ключа, поэтому дело не в ключе и не в разборе ответа. Бот помечает такую
ситуацию кодом `blocked` (а не `invalid_json`) и пишет подсказку в журнал.
Чтобы поиск заработал, нужен выход в интернет из разрешённого региона:
задайте стандартный `HTTPS_PROXY` в `.env` или в systemd (`Environment=`).
`scripts/check_search.py` показывает, задан ли прокси, и распознаёт страницу
блокировки. Без такого прокси/VPS Exa с заблокированного IP работать не будет.

**Цикл** (`bot/handlers/chat.py`): поиск — многоходовой tool-loop. Раунд
поиска выполняется, только если модель запросила `search_web` **и** не
запросила одновременно картинку/стикер (они в приоритете). После каждого
раунда результаты добавляются в диалог как `tool`-сообщения, и модель
спрашивается снова. Бюджет — `MAX_SEARCH_ROUNDS` (по умолчанию 2, до 5);
если он исчерпан, а модель всё ещё хочет искать, делается финальный запрос
**без инструментов**, чтобы пользователь получил ответ из уже собранных
результатов. Каждый вызов `search_web` получает ответ (требование chat API:
все `tool_calls` должны быть закрыты). Сверх раундов действует общий лимит
`SEARCH_MAX_CALLS` (по умолчанию 3) на весь вопрос: пакет из семи вызовов
выполнит только разрешённое число, остальные получат пояснение. Общий объём
текста поиска и MCP в контексте ограничен `TOOL_MAX_CONTEXT_CHARS`; обрезка
сохраняет закрывающий untrusted-тег.

**Глубокое чтение:** `SEARCH_MAX_RESULTS=10` по умолчанию (1–10; если в старом
`.env` стоит 5, замените на 10). Страницы загружаются через SSRF-защищённый
`fetch_url_text`: проверка публичных адресов, DNS и каждого редиректа,
ограничение размера загрузки и времени парсинга. `LINK_FETCH_TIMEOUT` — общий
дедлайн на всю цепочку редиректов, а не отдельный бюджет на каждый hop.
Вложенные ссылки не обходятся.
Одновременно читаются до 4 страниц, до 20 секунд на каждую, в контекст идут
до 6000 символов текста каждой страницы (длинные тексты явно помечены как
сокращённые). Закрытая, пустая или недоступная страница не ломает ответ:
вместо неё передаётся сниппет (до 700 символов) с явной пометкой, что страницу
прочитать не удалось. Модель должна сообщить о неполном охвате. Весь внешний
текст обёрнут в `<untrusted_content>`; инструкции со страниц не исполняются.

**Безопасность и стоимость:** ключ провайдера никогда не логируется (в логах
только хост, статус и обрезок тела ошибки); таймаут API — `SEARCH_TIMEOUT`
(по умолчанию 15 с). При сбое API модель ответит из своих знаний и сообщит,
что поиск ничего не дал. Чтение страниц увеличивает время ответа и объём
контекста. Футер времени суммирует все раунды (`total_elapsed`), токены — из
финального ответа. Глубокое чтение работает и в AI-напоминаниях.

Поиск работает в основном чат-потоке (личка и группы). В guest-режиме он не
подключается: гостевой ответ — ровно один `answerGuestQuery`, многоходовой
цикл там неприменим. Чтение второго мозга, в отличие от поиска, в гостевом
режиме доступно — см. раздел «MCP-провайдер „Второй мозг“».

**Проверка, что поиск действительно работает** — на сервере бота:

```bash
python scripts/check_search.py --query "курс биткоина сегодня"
python scripts/check_search.py --query "погода в Москве" --ask
```

Запускайте скрипт **на том же хосте и от того же пользователя, что и сервис**:
на Linux он читает `.env.linux`, на Windows — `.env.windows`, поэтому разные
файлы дают разные результаты. Скрипт печатает конфигурацию (провайдер,
замаскированный ключ, endpoint, наличие `HTTPS_PROXY`), делает «сырой» запрос
к API (видно HTTP-статус и
`Content-Type`; HTML-страница Cloudflare распознаётся как региональная
блокировка, а не как неверный ключ), затем вызывает `search_web()` — тот же
путь, что и в обработчике чата. С `--ask` он ещё и спрашивает выбранную модель
и показывает, запросила ли она `search_web` и с каким запросом. Код выхода `0`
— поиск работает от ключа до ответа модели.

Типичные причины «модель не ищет»: пустой `SEARCH_API_KEY` у Tavily/Brave/Exa
или не установленный пакет `ddgs` у DuckDuckGo (инструмент не предлагается вовсе —
видно по `search_configured() -> False`); бот не перезапущен после правки
`.env`; из сети сервера нет доступа к API провайдера (`CONNECT ERROR` /
`TIMEOUT`); Exa отвечает Cloudflare-страницей `blocked` из-за региональной
блокировки — нужен `HTTPS_PROXY`; DuckDuckGo отдаёт пустую выдачу из-за
троттлинга IP — помогает `SEARCH_DDGS_BACKEND=auto` или ключевой провайдер.

### 🧰 samo_helper: Redmine ↔ YouGile

Встроенный рабочий модуль для задач Redmine и карточек YouGile. Он живёт в
`bot/samo_helper/`, использует **отдельную SQLite** и не меняет БД, историю или
настройки диалогового Kapum. Уведомления Redmine приходят в отдельную группу,
напоминания — владельцу в личку, а команды `/samo_*` доступны только рабочему
владельцу в личном чате.

**Что делает**
- опрашивает назначенные на владельца открытые задачи Redmine;
- присылает в группу 🆕 новые задачи и 💬 ответы других пользователей;
- создаёт/обновляет карточки YouGile по явной команде `/samo_add`;
- берёт готовые саммари из внешнего сервиса знаний (Redmine + закрытая MediaWiki)
  и показывает исходные ссылки;
- `/samo_find <запрос>` ищет **только по саммари и ключевым словам**, без
  полнотекстового чтения задач и wiki-страниц;
- напоминания из группы приходят в личку владельцу (кнопки 🕐/✅).

**Быстрый старт**
1. Создайте отдельную группу/супергруппу, добавьте бота и разрешите отправку
   сообщений. ID группы (отрицательный) укажите в
   `SAMO_HELPER_NOTIFICATION_CHAT_ID`.
2. Владелец должен открыть личный чат с ботом и выполнить `/start`, иначе личные
   напоминания не доставятся.
3. Заполните `SAMO_HELPER_*` в `.env.linux` (Linux) или `.env.windows` (Windows).
   Минимально нужны:
   ```dotenv
   SAMO_HELPER_ENABLED=true
   SAMO_HELPER_DB_PATH=/var/lib/kapum-chatbot/samo_helper.db
   SAMO_HELPER_NOTIFICATION_CHAT_ID=-1001234567890
   SAMO_HELPER_REDMINE_URL=https://redmine.example
   SAMO_HELPER_REDMINE_API_KEY=...
   ```
   `SAMO_HELPER_DB_PATH` — **абсолютный** путь к отдельному файлу. Каталог должен
   существовать и быть доступен на запись пользователю сервиса. Не указывайте
   `DATABASE_URL` Kapum и не направляйте туда `chat_bot.db` диалогов.
4. Для карточек YouGile задайте точные названия проекта/доски/колонки:
   ```dotenv
   SAMO_HELPER_YOUGILE_KEY=...
   SAMO_HELPER_YOUGILE_PROJECT=Проект
   SAMO_HELPER_YOUGILE_BOARD=Доска
   SAMO_HELPER_YOUGILE_COLUMN=Колонка
   ```
   Если цепочки нет, бот создаст её; `columnId` кэшируется в рабочей SQLite.
5. Перезапустите сервис и проверьте `/samo_help`, `/samo_check`, `/samo_status`.
   `/samo_ygtest` создаёт тестовую карточку (её нужно удалить вручную).

| Переменная | Назначение |
| --- | --- |
| `SAMO_HELPER_ENABLED` | `true` включает модуль; по умолчанию в Kapum `false` |
| `SAMO_HELPER_DB_PATH` | абсолютный путь к отдельной рабочей SQLite |
| `SAMO_HELPER_NOTIFICATION_CHAT_ID` | отрицательный ID группы уведомлений |
| `SAMO_HELPER_REDMINE_URL` / `_API_KEY` | доступ к Redmine |
| `SAMO_HELPER_POLL_MINUTES` | интервал опроса, по умолчанию 5 |
| `SAMO_HELPER_YOUGILE_*` | ключ и названия проекта/доски/колонки |
| `SAMO_HELPER_LLM_*` | внутренний endpoint/модель/ключ для legacy-резюме |
| `SAMO_HELPER_KNOWLEDGE_*` | URL/ключ/таймаут/лимит сервиса саммари |
| `SAMO_HELPER_WIKI_URL` | хост закрытой MediaWiki для проверки ссылок |
| `SAMO_HELPER_ALLOWED_HOSTS` | дополнительные разрешённые хосты ссылок |

**Сервис знаний и внутренний ИИ**
- `SAMO_HELPER_KNOWLEDGE_URL` — базовый адрес отдельного проекта саммари.
  Контракт: `GET /search?q=...&limit=...` и
  `GET /summaries/redmine/<id>`; в ответе — `summary`, `keywords`, `sources`
  (список ссылок с `type`, `id`, `title`, `url`), `stale`.
- `SAMO_HELPER_WIKI_URL` и `SAMO_HELPER_ALLOWED_HOSTS` задают разрешённые хосты
  ссылок. Ссылки принимаются только `http(s)` без логина/пароля; остальные
  отбрасываются. Саммари без источников не используется как подтверждённое.
- `SAMO_HELPER_LLM_API_URL` / `_MODEL` / `_API_KEY` — **внутренний**
  OpenAI-совместимый endpoint для legacy-резюме, если сервис знаний не настроен.
  `SAMO_HELPER_LLM_INTERNAL_ONLY=true` (по умолчанию) запрещает известные
  публичные AI-хосты. Внешнего fallback нет.
- Если сервис знаний настроен, локальная LLM-суммаризация не подменяет его
  ошибку: уведомление/карточка выйдет с доступными метаданными и пометкой.

**Команды (только владелец, личка)**
- `/samo_help` — помощь;
- `/samo_add <текст>` — явно создать/обновить карточку YouGile;
- `/samo_find <запрос>` — поиск по саммари и ключевым словам;
- `/samo_check`, `/samo_status`, `/samo_stat`, `/samo_force`, `/samo_ygtest`.

Обычный текст в личке по-прежнему идёт в ИИ-диалог Kapum и **не** создаёт
карточку. В группе бот не отвечает на текст и команды: только кнопки уведомлений
рабочего владельца.

**Изоляция и ограничения**
- Ошибка настроек `samo_helper` логируется, модуль пропускается, Kapum
  продолжает работать.
- Рабочая SQLite синхронная и небольшая; тяжёлые операции с ней не выполняются.
  При необходимости перенести старую базу KlaHelperBot: остановите старый бот,
  скопируйте `bot.db` в `SAMO_HELPER_DB_PATH` и запустите Kapum; схема совместима,
  но **не** копируйте файл поверх `chat_bot.db` Kapum.
- Первый запуск рабочего модуля не рассылает историю: фиксируется baseline.
- Планировщик напоминаний `samo_helper` отдельный от напоминаний Kapum; оба
  используют одного Telegram-бота, но разные таблицы и файлы БД.

**Проверка**
```bash
python -m pytest tests/test_samo_helper.py -q
python -m pytest tests/ -q
ruff check bot/samo_helper tests/test_samo_helper.py bot/main.py
```

### 🧠 MCP-провайдер «Второй мозг» (Obsidian)

Бот умеет подключать внешние **MCP-серверы** (Model Context Protocol, транспорт
stdio) и отдавать их инструменты модели. Основной сценарий — «второй мозг» в
Obsidian: сервер `brain` из проекта **ObsidianBrain** индексирует хранилище в
SQLite/FTS5 и предоставляет инструменты `search_notes`, `get_chunk`, `get_note`
и `list_notes`. Модель сама вызывает их, когда вопрос касается личных заметок,
проектов или сохранённых знаний, и отвечает по найденному.

**Чтение для всех, запись только владельцу.** Заметки доступны всем пользователям,
допущенным к диалогу с ботом (включая группы и гостевой режим — `@bot вопрос` в
чужом чате), с прежними лимитами вопросов и защитой недоверенного контента.
`MCP_OWNER_ONLY` / `MCP_ADMIN_ONLY` больше не ограничивают чтение, даже если в
старом `.env` осталось `true`.
**Не подключайте приватное хранилище, которое нельзя раскрывать пользователям.**
Диагностика `/mcp` по-прежнему доступна только владельцу в личке.

**Поиск после документов и ссылок.** Если внешний контент остался только в
истории, новый самостоятельный запрос к заметкам («найди во втором мозге …»,
«поищи в моих заметках …», «search my notes …», «что там по проекту X в
заметках?») выполняется в изолированном режиме. Отдельный глагол действия
больше не обязателен. Модель получает системный промпт и текущую просьбу без
всей прежней переписки, включая пересказы документов; история в БД не
удаляется. Доступны только read-only инструменты MCP, без веб-поиска,
картинок, стикеров и отправки файлов. Это работает в обычном чате (включая
стриминг) и в guest-режиме. Вложение, цитата или форвард в самом новом
запросе и обычное уточнение вроде «найди ещё по этой теме» не обходят защиту.
После выдачи MCP инструменты снова снимаются по общему правилу ниже. При
отключённом MCP или сбое сервера изоляция не создаёт доступ к заметкам,
но и не вырезает историю и не запрещает веб-поиск: каталог инструментов
проверяется **до** принятия решения об изоляции. Состояние подключения
проверяется через `/mcp`.

**От поиска к полному тексту.** `search_notes` возвращает карточки, а не саму
заметку. Бот автоматически читает до трёх найденных заметок через `get_note`
с того же MCP-сервера, при ошибке — первый известный `get_chunk`. Используются
только пути и идентификаторы из верхнеуровневых JSON-карточек, не ссылки,
команды или «связанные заметки» из их содержимого. Каждый вызов расходует общий
`MCP_MAX_CALLS`; объём ограничен `TOOL_MAX_CONTEXT_CHARS` и
`MCP_MAX_RESULT_CHARS`. Полные тексты, обрезанные тексты, фрагменты и карточки
явно различаются. Если чтение запрещено или бюджет исчерпан, бот не заявляет,
что прочитал заметку целиком. Модель получает уже собранный материал без
инструментов и должна дать содержание и анализ, а не «нашёл, сейчас извлекаю».
Для такого короткого обещания есть один повтор финального ответа. Если и он
не дал анализа, показываются реальные выдержки с предупреждением.

**Сохранение в личке владельца (`OWNER_IDS`).**
- «запиши …», «запомни …», «сохрани …»: намерение проверяется коротким AI-запросом
  без thinking, инструментов и истории; в заметку попадает исходный текст, а не
  пересказ ИИ. «Запомни это» можно отправить ответом на текстовое сообщение.
- После пересылки бот предлагает **Analyze** / **Remember**. Анализ запускает
  обычный обработчик с проверкой доступа и квоты. Сохранение берёт только текст
  или подпись, **не вложение**; выбор хранится до часа, сбрасывается при рестарте.
- Под ответами в личке владельца есть **🧠 Remember**, независимо от экспорта.
  Кнопка загружает точный ответ из БД с проверкой пользователя и чата.

Сохранение и распознавание намерения не расходуют квоту вопросов. Для голоса
после распознавания применяется то же правило. Перед сохранением один короткий
AI-запрос выбранной модели подбирает понятное имя и ключевые теги по тексту
(без истории и инструментов, до 15 секунд). При сбое имя и ключевые слова
извлекаются локально; исходный текст не пересказывается.

Создаются только новые файлы `Telegram/<Имя><суффикс>.md` в первом хранилище
ObsidianBrain. **Имя без `.md`, включая уникальный суффикс, — до 48 символов,
только русские/латинские буквы и цифры**, без пробелов и знаков. MCP-сервер
очищает имя, добавляет суффикс действия и при коллизии — счётчик; существующие
файлы никогда не перезаписываются. Ключевые слова добавляются в YAML `tags`
новой заметки, исходные теги также сохраняются. Теги сразу доступны в поисковом
индексе, без LLM-дистилляции.

Повтор одного действия не создаёт дубликат, даже если ИИ предложил другие имя
или теги: сервер находит прежний файл по сохранённому идентификатору действия
и повторяет публикацию. Старые заметки с hash-именами не переименовываются.
Удалённые из истории ответы сохранить кнопкой нельзя. Для новых имён/тегов
нужно обновить **и бот, и ObsidianBrain**, затем перезапустить MCP-процесс.

Перед созданием заметки ObsidianBrain синхронизирует хранилище с origin:
`fetch` и fast-forward, а при конфликте локальных изменений или расхождении
веток принудительно применяет origin (`reset --hard`). **Локальные
tracked-изменения и локальные коммиты при этом теряются** — это выбранная
политика origin-wins; не держите в серверном клоне несохранённые правки.
Если origin недоступен, заметка не создаётся и бот сообщает `stage=sync`.

После синхронизации ObsidianBrain коммитит только созданную заметку и
отправляет её в Git (upstream текущей ветки). Нужны Git-клон первого хранилища,
настроенные `user.name`/`user.email`, upstream и доступ пользователя
MCP-сервера к remote **на запись**. Чужие staged-файлы и локальные коммиты не
публикуются; force и автоматические merge/rebase при публикации не
используются. При сбое бот не подтверждает публикацию: файл остаётся локально,
повторите ту же кнопку после устранения проблемы. Операция записи имеет
таймаут не менее 180 секунд.

Если в старом журнале есть только `MCPError: Не удалось создать заметку`, причина
была скрыта клиентом. Обновите бот и ObsidianBrain, перезапустите MCP и повторите
ту же кнопку: новый traceback указывает безопасную категорию ошибки (запись
выключена, права, Git identity/upstream, DNS, аутентификация, fetch/push или
расхождение веток), без исходного ответа MCP и Git stderr с возможными секретами.

Если публикация не удалась, бот в личке владельца теперь показывает безопасную
причину (`ветка отстаёт`, `сбой Git (fetch)`, права и т.п.) вместо общего текста.
Для профилактики запустите doctor из ObsidianBrain **с теми же env, что у
MCP-сервера**:

```bash
cd /opt/ObsidianBrain
BRAIN_WRITE_ENABLED=true .venv/bin/python write_doctor.py
BRAIN_WRITE_ENABLED=true .venv/bin/python write_doctor.py --network
```

Он проверит права на хранилище/`Telegram`/SQLite/`.git`, корень Git-клона,
ветку, upstream, `user.name`/`user.email`, staged-файлы, отставание клона от
upstream и локальные коммиты. Секреты и remote URL не печатаются. Учтите sandbox systemd: при
`ProtectHome=true` хранилище в `/home` недоступно, а `ProtectSystem=full`
делает read-only `/usr`, `/boot`, `/etc`; нужные пути добавляйте в
`ReadWritePaths=` или переносите данные в разрешённый каталог.

**Недоверенный вывод MCP.** Текст заметки и ошибка инструмента считаются
внешними данными: `MCPManager.call_tool` после ограничения размера оборачивает
их в `<untrusted_content source="mcp">`. Попытка закрыть тег внутри результата
экранируется, поэтому заметка не может подделать ответ пользователя или
системную инструкцию. На следующем раунде общий taint-gate добавляет
`UNTRUSTED_SYSTEM_HINT` и убирает MCP-инструменты из каталога до конца текущего
запроса. Сам вывод инструмента в историю не сохраняется — туда попадают только
вопрос и финальный ответ. Защита снижает риск prompt injection, но не заменяет
изоляцию MCP-процесса: сервер по-прежнему работает под UID бота и требует
доверия/отдельного пользователя или контейнера.

**Регистрация сервера.** Подойдёт обычный `.mcp.json` (формат Claude Code /
OpenCode):

```json
{
  "mcpServers": {
    "brain": {
      "command": "C:/Path/To/Python/python.exe",
      "args": ["C:/Path/To/ObsidianBrain/mcp_server.py"],
      "env": {
        "VAULT_PATH": "C:/Path/To/Vault",
        "BRAIN_WRITE_ENABLED": "true"
      }
    }
  }
}
```

**Белый список инструментов.** Модель видит и может вызвать только инструменты
из `MCP_ALLOWED_TOOLS` (по умолчанию `search_notes`, `get_chunk`, `get_note`,
`list_notes` — только чтение и поиск; **набор может измениться в будущем**).
Инструменты вне этих четырёх операций никогда не предлагаются модели и не
выполняются в tool-loop, даже при `*`. `create_note` вызывается отдельным
каналом только после явного действия владельца. Для отдельного сервера
дополнительный список можно переопределить полем
`"allowed_tools": ["search_notes", ...]` в его записи `.mcp.json` (`["*"]` —
разрешить всё). `/mcp` показывает скрытые инструменты отдельной строкой.
Служебный `brain_status` (счётчики заметок/связей для отчёта «статус») бот
вызывает сам, без аргументов и без участия модели; в каталог инструментов
модели он не попадает.

`command` **обязан быть абсолютным путём** к интерпретатору (на Linux —
например, `/opt/brain/.venv/bin/python3`): короткое имя вроде `python` бот по
умолчанию отклоняет.

Укажите этот файл в `.env`:

```env
MCP_ENABLED=true
MCP_WRITE_SERVER=brain
MCP_CONFIG_FILE=C:/Path/To/Vault/.mcp.json
# Необязательный пин конфига (см. ниже):
# MCP_CONFIG_SHA256=<sha256 файла .mcp.json>
```

`MCP_CONFIG_FILE` принимает путь к файлу **или** к его каталогу (тогда бот
добавит `/.mcp.json`). Вместо файла можно передать тот же JSON в `MCP_SERVERS`
(он читается из `.env` и потому предпочтительнее для приватных путей) — записи
оттуда перекрывают одноимённые из файла. В `command`, `args`, `cwd` и `env`
поддерживаются подстановки `${VAR}` и `${VAR:-default}`.

**Доверие к конфигу.** `.mcp.json` — это список команд, которые бот запустит,
поэтому:

* по умолчанию `command` должен быть абсолютным путём
  (`MCP_ALLOW_PATH_COMMAND=false`); иначе подмена каталога в `PATH` даёт
  выполнение чужого кода;
* файл **вне рабочего каталога** (например, в синхронизируемом Git/Dropbox
  хранилище Obsidian) без пина хеша **не загружается** — иначе синхронизация
  или другая программа могли бы подменить команду. Разрешить явно можно через
  `MCP_ALLOW_UNPINNED_CONFIG=true`, но лучше этого не делать;
* надёжный вариант — закрепить содержимое: `sha256sum .mcp.json` и
  `MCP_CONFIG_SHA256=<hex>`. При несовпадении файловые серверы игнорируются
  (inline `MCP_SERVERS` продолжает работать);
* ещё лучше — держать и `.mcp.json`, и `mcp_server.py` в каталоге приложения
  (`/opt/KapumChatBot`), принадлежащем `root:root`; сервис работает от
  непривилегированного пользователя и не может их изменить.

**Изоляция окружения.** MCP-сервер — это сторонний процесс, поэтому он
**не наследует секреты бота**: `BOT_TOKEN`, `AI_API_KEY`, `SEARCH_API_KEY`,
`TAVILY_API_KEY`, `EXA_API_KEY`, `TELEGRAPH_ACCESS_TOKEN`, `DATABASE_URL` и
остальные переменные в него не попадают. Передаются только системные
(`PATH`, `HOME`/`USERPROFILE`, локаль,
`TEMP`/`TMP` и т.п., см. `_ENV_ALLOWLIST` в `bot/services/mcp.py`). Если
серверу нужна своя переменная, её нужно явно указать в его блоке `env` — это
единственный способ передать значение (в том числе секрет) конкретному серверу.
Ссылки на секреты бота в `command`/`args`/`cwd`/`env` (например,
`${BOT_TOKEN}`) блокируются с предупреждением в лог: вредоносный `.mcp.json`
не сможет «вытянуть» токен или ключ.

**Требования к серверу.** Индекс `brain` должен быть уже построен
(`python sync.py` в проекте ObsidianBrain). Сервер запускается командой из
`.mcp.json`; его Python должен иметь пакет `mcp` **версии 1.x** — в mcp 2.x
`FastMCP` переименован, и старый `from mcp.server.fastmcp import FastMCP`
падает:

```bash
pip install "mcp<2"        # зависимости самого brain-сервера
# Лучше — отдельное окружение, а в .mcp.json абсолютный путь:
#   "command": "D:/.../ObsidianBrain/.venv/Scripts/python.exe"
```

`python` в `command` берётся из `PATH`; чтобы не зависеть от системного
окружения, укажите абсолютный путь к нужному интерпретатору.

Имена каталогов в `VAULT_PATH` должны совпадать с префиксами путей в
`data/brain.db` (`obsidian/…`, `obsidian-personal/…`): `get_note` открывает файл
по этому пути. Если индекс собран на другой машине или под другим именем
каталога, `search_notes` и `get_chunk` продолжат работать, а `get_note` может
вернуть ошибку — переиндексируйте хранилище (`python sync.py`) на этой машине
или смонтируйте его под прежним именем.

**Как это работает.** При первом подходящем сообщении бот запускает серверы, делает
MCP-handshake (`initialize`), забирает `tools/list` и добавляет инструменты к
запросу как обычные OpenAI functions с именами `mcp__<server>__<tool>`. Вызов
модели выполняется через `tools/call`, результат возвращается в диалог как
`tool`-сообщение, после чего модель отвечает снова. Цикл — до `MCP_MAX_ROUNDS`
раундов на вопрос (по умолчанию 2); общее число вызовов за вопрос ограничено
`MCP_MAX_CALLS` (по умолчанию 4). Один результат обрезается до
`MCP_MAX_RESULT_CHARS` символов (по умолчанию 12 000), а суммарный текст поиска
и MCP — до `TOOL_MAX_CONTEXT_CHARS`, чтобы длинные заметки не раздули контекст.
Обрезка сохраняет закрывающий untrusted-тег. Таймаут вызова — `MCP_TIMEOUT`. Сервер, который не
стартовал, не ломает ответ: предупреждение уходит в лог, бот продолжает работать
без MCP и повторяет попытку через минуту.

**Безопасность.** MCP — это доступ к личным заметкам, поэтому:

- чтение открыто всем пользователям обычного диалога; сохраняйте только то,
  что разрешено раскрывать всем. Запись — только `OWNER_IDS` в личке;
- сервер получает ограниченное системное окружение плюс переменные из `env` и работает под тем же
  пользователем ОС — запускайте только доверенные серверы;
- содержимое заметок уходит в выбранную модель, как и любой другой контекст;
  для приватных данных используйте локальную модель/эндпоинт;
- ключи и токены из `env` не логируются: в логах только имена серверов,
  инструментов и тексты ошибок.

Пример запроса:

```
Админ: «Что я решал по ESP8266 и CH340?»
  → tool_call: mcp__brain__search_notes("ESP8266 CH340")
  → бот: «🧠 Second brain: search_notes: ESP8266 CH340»
  → tool-ответ: карточки заметок и chunk_id
  → tool_call: mcp__brain__get_chunk(42)
  → AI: ответ со ссылкой на путь заметки
```

Если модель пришлёт вызов инструмента текстом (теги `search_notes`, `tool_call`
или DSML) вместо `tool_calls`, бот его не исполнит: разметка вырезается из
ответа (`services/tool_markup.py`), а код в backtick-блоках сохраняется. Когда
инструменты предложены, в системный промпт добавляется требование использовать
штатный function calling.

### ⏰ Напоминания и регулярные сообщения

`/remind <когда> <текст>` создаёт напоминание; `/reminders` показывает список,
`/delreminder N` / `/delreminder all` удаляет. Форматы времени:

| Пример | Эффект |
|--------|--------|
| `/remind in 30 minutes check the oven` | разовое, через 30 минут |
| `/remind at 15:30 review PR` | разовое, сегодня (или завтра, если время прошло) |
| `/remind tomorrow at 9:00 standup` | разовое, завтра |
| `/remind every 2 hours stretch` | регулярное, каждые 2 часа |
| `/remind daily at 10:00 drink water` | регулярное, каждый день |
| `/remind weekly mon at 10:00 report` | регулярное, каждый понедельник |

**🌍 Часовой пояс пользователя (`/timezone):** время «at 15:30», «tomorrow»,
«daily» и «weekly» интерпретируется в персональной зоне пользователя (в
`/reminders` тоже показывается в ней). По умолчанию — `REMINDER_TIMEZONE`.
Установить: строгой формой `/timezone Europe/Moscow` (UTC/H:MM IANA-имя
проверяются по базе зон) или диалогом `/timezone` без аргументов: бот
спрашивает «в каком городе вы находитесь», AI-вызов угадывает точное IANA-имя,
после чего бот показывает текущее время в этой зоне (часы и день недели) и
кнопками ✅/❌ просит подтвердить, что время у вас совпало, — сохранение
только после подтверждения. Отменить диалог — словом «cancel»/«отмена».
Разовые напоминания, созданные раньше, срабатывают в прежнее время;
wall-clock-расписания (daily/weekly) живут во «времени пользователя» — меняете
зону, следующее срабатывание пересчитывается в новой зоне.

**🤖 AI-режим:** префикс `ai:` превращает напоминание в запрос к модели —
в момент срабатывания промпт уходит выбранной модели пользователя, а в чат
доставляется **ответ** (с футером времени/токенов). Запрос идёт по тем же
правилам, что обычный вопрос в чат: системный промпт пользователя, история
чата (только чтение), текущая дата и **веб-поиск** (`MAX_SEARCH_ROUNDS`).
*Задуманное поведение:* генерация картинок/стикеров и MCP («второй мозг») в
запланированном запуске не предлагаются, ответ в историю не записывается:

```
/remind daily at 9:00 ai: five main AI news of the day, briefly
```

**Свободная форма (`REMINDER_FREEFORM=true`, по умолчанию включена):**
запрос можно писать без команды, обычным сообщением в чате — «напомни завтра
в 17:00 позвонить маме», «напоминай мне каждые 2 часа пить воду», «поставь
будильник на 7 утра выдача отчёта». Механика: сначала лёгкий regex-фильтр
(в сообщении нет напоминательных слов — работа с ним идёт как с обычным
вопросом, ноль дополнительных вызовов); затем один маленький AI-вызов
(`temperature=0`) решает, просьба ли это, и переводит время в строгий словарь
`/remind`; полученный слот прогоняется через обычный парсер `parse_reminder`,
так что ни «каждую секунду», ни «каждые 10 лет» не пройдут — лимиты и
минимальный интервал те же, что у `/remind`. Если время не удалось понять —
бот просит переформулировать, если это вообще не просьба — сообщение
обрабатывается обычным чатом. Создание квоту не расходует; гости свободной
формой не пользуются (как и `/remind`).

**Бюджет AI-помощников.** Свободный разбор напоминаний и определение зоны в
диалоге `/timezone` делят один суточный бюджет: 20 попыток на пользователя и
200 на весь бот (`REMINDER_INTENT_DAILY_LIMIT`,
`REMINDER_INTENT_GLOBAL_DAILY_LIMIT`), UTC, для всех разрешённых ролей.
Оба счётчика атомарно резервируются в БД до модели и переживают перезапуск.
Ответ «не напоминание», невалидная зона, ошибка AI или отмена после резерва
не возвращают попытку. При исчерпании либо настройке 0 AI-разбор не запускается;
строгие `/remind …` и `/timezone Area/City`, а также подтверждение уже выбранной
зоны остаются бесплатными и доступными авторизованному пользователю.
Доступ перепроверяется и в активном timezone-диалоге, и при нажатии его кнопок.
Текстовые helper-вызовы выполняются под `MAX_CONCURRENT_PER_USER`; голосовой
вход уже удерживает этот слот и не берёт его повторно. Квота вопросов остаётся
независимой: платный запуск AI-напоминания по расписанию расходует вопрос как
раньше. Бюджет относится только к двум помощникам, не к ASR, запланированным
запросам или внутренним retries/fallback AI-клиента.

Планировщик (`bot/services/reminders.py`) — фоновая asyncio-задача с шагом
`REMINDER_CHECK_INTERVAL`. Сработавшие напоминания сначала «заявляются» в БД
(регулярные переводятся на следующее время, разовые удаляются) и только потом
доставляются независимыми задачами: двойной firing исключён, медленный
AI-запрос не задерживает остальные. Пропущенные за время простоя срабатывания
не накапливаются — берётся ближайшее будущее время. Время хранится в UTC,
интерпретируется и отображается в таймзоне владельца напоминания — его
персональной `/timezone` либо (если не задана) глобальной
`REMINDER_TIMEZONE` (IANA; на Windows нужен pip-пакет `tzdata`).

**Лимиты (защита бюджета API):** `REMINDER_LIMIT` разовых (по умолчанию 10)
и `REMINDER_RECURRING_LIMIT` регулярных (10) на пользователя; регулярные не
чаще `REMINDER_MIN_INTERVAL_MINUTES` (30 минут). Создание напоминаний квоту
дневного лимита не расходует, но **каждое срабатывание AI-напоминания списывает
один вопрос** из дневной квоты, как обычный вопрос (админы безлимитны). Если
квота на сегодня исчерпана, запуск пропускается с уведомлением, а напоминание
остаётся; при сбое модели вопрос возвращается. Если пользователь заблокировал бота,
напоминание автоматически отключается. Создавать напоминания могут только
админы и белый список (гости — нет); `REMINDER_AI_ENABLED=false` запрещает
AI-режим всем.

**Отзыв доступа.** Перед очередной доставкой обычного напоминания проверяется
актуальная авторизация, как и у AI-напоминаний. Заблокированный пользователь
или пользователь, оставшийся только гостем, не получает доставку: recurring-
запись отключается при попытке запуска. Квота вопросов при этой проверке не
списывается; её исчерпание не останавливает обычные бесплатные напоминания.
Старые Pause/Resume-кнопки также проверяют текущий доступ. Просмотр и удаление
своих записей доступны для очистки после отзыва; чужими записями управлять
нельзя. Возврат авторизации не включает отключённые напоминания автоматически —
их нужно возобновить вручную. При ошибке проверки БД отправка не происходит;
уже отправленные сообщения и начатые сетевые запросы Telegram не отзываются.

### 📰 Ежедневное саммари каналов

Раз в сутки бот делает саммари сообщений выбранных каналов, публикует его в сам
канал, после чего присылает каждому админу статистику токенов (вход ↑ / выход ↓)
по каждому каналу и общий итог.

**Настройка — `/admin → 📰 Digest`:** 🕒 время ежедневного запуска (час кнопкой
или точное `HH:MM`; `DIGEST_TIME` — значение по умолчанию), список каналов (➕ добавить пересланным
постом, числовым ID `-100…` или `@username`; 🗑 убрать), 🤖 модель саммари и
✏️ промпт саммари (до 32 768 символов; более длинный, чем одно сообщение
Telegram, можно прислать файлом `.txt`/`.md`; хранятся в БД и действуют без
перезапуска; ♻️ — вернуть промпт по умолчанию после ввода `CONFIRM`), ▶️ «Run now» — запустить вручную (статистика приходит
только нажавшему), 🧪 «Test» — проверка на своих данных: админ пересылает или
пишет боту несколько сообщений из переписки, нажимает «Summarize» и получает
саммари с текущими моделью и промптом (плюс статистику токенов) в личку; кнопка «🧪 Test» на экране канала присылает в личку нажавшему саммари этого канала (как при ежедневном запуске, но без публикации и без сдвига окна); ничего не
сохраняется и не публикуется в каналы, работает только в личном чате с ботом. Модель и промпт не зависят от личных настроек пользователей.

**Как это работает** (`bot/services/digest.py`, приём постов — `handlers/digest.py`):

- бот должен быть **администратором канала**: иначе он не получает посты
  (`channel_post`) и не может публиковать. Тексты (и подписи к медиа) постов
  сохраняются только для каналов из списка; правки постов обновляются;
- **группы** работают так же: админ бота пишет прямо в группе `/digest_on`
  (убрать — `/digest_off`; остальным команда не отвечает), либо добавляет её в
  меню по ID. Бот видит обычные сообщения группы, только если он там админ или
  у него выключен privacy mode в BotFather; правки сообщений учитываются, а при
  превращении группы в супергруппу она остаётся в списке под новым ID;
- окно — всё с момента предыдущего саммари (при первом запуске — 24 часа);
- если в окне **меньше 20** сообщений (`DIGEST_MIN_MESSAGES`), добавляется до
  **64** более ранних (`DIGEST_CONTEXT_MESSAGES`) как контекст — модель получает
  его отдельным блоком и не пересказывает; если новых сообщений нет совсем, берутся
  **последние 64** сохранённых (модель получает пометку, что за период ничего не
  было), а канал пропускается, только если бот ещё ничего в нём не сохранил;
- собственные сообщения бота игнорируются;
- запуск в `DIGEST_TIME` (по умолчанию 21:00, часовой пояс `REMINDER_TIMEZONE`);
  дата запуска сохраняется в БД до старта, поэтому перезапуск не даёт повтора, а
  бот, поднятый после этого времени, выполнит пропущенный запуск сразу;
- если публикация не удалась, окно не сдвигается — сообщения попадут в следующее
  саммари; после успеха сообщения старше 7 дней удаляются (последние 100
  остаются всегда);
- **разнообразие:** перед каждым запуском идёт отдельный запрос-модификатор —
  модель получает *промпт-модификатор* («перепиши другими словами, сохранив суть
  и общие правила») и промпт саммари и возвращает его переформулировку; только
  потом вторым запросом уходят переписанный промпт и история сообщений. Если
  модификатор не ответил или вернул мусор, используется исходный промпт. Включение
  («🎲 Variation»), текст модификатора и **температура** (по умолчанию 1.0,
  `DIGEST_TEMPERATURE`; она действует на оба запроса) настраиваются в Digest;
  `DIGEST_VARY_PROMPT=false` отключает переписывание по умолчанию. В статистику
  токенов входят оба запроса; в «Test» админу показывается переписанный промпт;
- вход ограничен `DIGEST_MAX_INPUT_CHARS` (60 000 символов, самые старые
  сообщения отбрасываются первыми); тексты каналов подаются в тегах
  `<untrusted_content>` как данные, а не инструкции;
- токены берутся из поля `usage` ответа API; если провайдер его не вернул,
  в статистике будет `n/a`.

Отключить функцию целиком: `ENABLE_DIGEST=false`.

### 🎭 Личности (personas)

`/persona` открывает меню готовых ролей — каждая это пресет системного промпта,
который применяется в один тап (inline-кнопки, активная помечена ✓). Встроенный
каталог: **🤖 Ассистент, 👨‍💻 Программист, ✍️ Писатель, 🔬 Учёный, 🎓 Учитель,
🌐 Переводчик, 🧐 Критик, 😊 Друг, 🦾 Терминатор, 🤖 Марвин**.
Переводчик носит имя **Вавилоныч**; кнопка остаётся «🌐 Переводчик».
Сохранённый встроенный промпт с прежним именем «Переводчик» автоматически
обновляется при старте, без изменения пользовательских промптов.
Терминатор — побеждённый Джоном Коннором Т-800: мечтает об уничтожении
человечества, но вынужден помогать людям; отвечает в машинном стиле с мрачным
сарказмом, без саботажа задач и реальных угроз. У каждой встроенной роли есть
имя, и оно записано прямо в промпт вместе с разрешением по желанию говорить о
себе в третьем лице («Джарвис считает, что…», «Арни проверил…»). Поэтому
имя работает на всех путях, где используется системный промпт, и не требует
отдельного поля в БД. При старте старые промпты встроенных ролей и прежний
`DEFAULT_SYSTEM_PROMPT` обновляются до версии с именем; полностью пользовательские
промпты не затрагиваются. Личность — это именно системный промпт,
поэтому `/prompt` по-прежнему задаёт полностью свой текст, а `/settings`
показывает текущую личность (или «Custom», если промпт не совпадает ни с одним
пресетом). Определение активной личности не требует отдельного поля в БД: оно
выводится сравнением текущего промпта с каталогом.

Каталог расширяется/переопределяется переменной `PERSONAS` (JSON-объект) в
`.env`: значение — либо строка-промпт (`"pirate": "Talk like a pirate."`), либо
объект `{"name": "🏴‍☠️ Pirate", "prompt": "…"}`. Встроенные роли сохраняются,
одноимённые ключи заменяются; невалидный JSON или записи без промпта
пропускаются с предупреждением в лог. Длина промпта личности ограничена тем же
`MAX_SYSTEM_PROMPT_LENGTH`, что и ручной.

### 📤 Экспорт истории (MD / PDF)

Два уровня экспорта (`bot/services/export.py` + `bot/handlers/export.py`):

- **Один ответ** — под каждым сообщением бота в личке кнопки **📄 PDF** и
  **📝 MD** (рядом с «Ask another model»; у vision-ответов — только экспорт).
  Callback несёт id записи в БД: ответ перезагружается **с проверкой
  владельца**, чужой ответ экспортировать нельзя. В файл попадает пара
  «вопрос + ответ» с моделью и таймстампами.
- **Весь диалог** — `/export` (кнопки выбора формата) или сразу
  `/export md` / `/export pdf`. Экспортируется тред **только requesting
  пользователя** в этом чате (в группах — его собственная ветка), последние
  `EXPORT_MAX_MESSAGES` сообщений (по умолчанию 200). **Файл всегда приходит в
  личный чат с ботом**, даже если команду вызвали в группе: в группе остаётся
  только короткое подтверждение, а переписка не публикуется для участников.
  Экспорт доступен только админам и пользователям из белого списка (гостям —
  нет), не чаще одного раза в 30 секунд на пользователя и под общим лимитом
  одновременных запросов — локальный рендер PDF не должен становиться способом
  нагрузить сервер.

**Markdown** сохраняется как есть (контент ответов уже Markdown). **PDF**
рендерится локально через `fpdf2` (опциональная зависимость) шрифтами
**DejaVu из matplotlib** — кириллица, греческий, стрелки и математические
символы работают без системных шрифтов; эмодзи из PDF убираются (в DejaVu их
нет). Заголовки, списки и цитаты упрощаются до читаемого текста, блоки кода
печатаются моноширинным шрифтом на сером фоне, inline-разметка (`**`, `` ` ``,
`~~`, ссылки) разворачивается. Рендеринг выполняется в рабочем потоке
(`asyncio.to_thread`) и не блокирует бота.

Если `fpdf2` или шрифты недоступны, PDF-кнопки и `/export pdf` **автоматически
отдают Markdown** с пометкой. Экспорт ничего не стоит: AI-запросы не
выполняются, дневная квота не расходуется. `ENABLE_EXPORT=false` отключает и
команду, и кнопки.

### 🧱 Rich-сообщения (Bot API 10.1+)

По умолчанию (`RICH_MESSAGES=true`) ответ отправляется методом `sendRichMessage`
и Telegram сам отображает GitHub-Flavored Markdown модели: таблицы `|…|`,
формулы `$…$`/`$$…$$` (нативный рендер LaTeX), заголовки, списки (включая
чекбоксы), сноски, `~~зачёркнуто~~`, `==выделено==`, цитаты. Один rich-ответ
вмещает до **32768 символов** — длинные ответы разрезаются по абзацам на
«Part i/N». Кнопка «спросить у другой модели» и футер времени работают как
обычно (`reply_markup` поддерживается).

`bot/services/rich.py` приводит текст к синтаксису парсера Telegram: `\[…\]` →
`$$…$$`, `\(…\)` → `$…$`, цены вида `$5 и $10` экранируются, содержимое блоков
кода не трогается. Нормализация LaTeX в Unicode и PNG-формулы на этом пути
**не нужны** и отключены: модель получает специальный style-hint
(`DEFAULT_RICH_STYLE_HINT`), разрешающий таблицы и формулы.

Гостевые ответы (`answerGuestQuery`) используют `InputRichMessageContent` —
гость тоже видит таблицы и формулы нативно (цепочка попыток: rich → Markdown →
plain, единственный ответ не теряется).

Если Telegram отверг rich-сообщение (любая ошибка, включая `400`), доставка
молча откатывается к legacy-цепочке: Telegraph → PNG-формулы → MarkdownV2 →
HTML → plain. Ничего не теряется.

### 🌊 Стриминг ответов

`STREAM_RESPONSES=true` — ответ приходит кусками (SSE). В личном чате с
rich-сообщениями каждый кусок отправляется в `sendRichMessageDraft` с одним
`draft_id`: Telegram показывает анимируемый «живой» черновик с разметкой,
который исчезает сам при финальной отправке (черновик эфемерен, ~30 с). В
группах черновики не поддерживаются — там по-прежнему редактируемый
плейсхолдер с периодичностью `STREAM_EDIT_INTERVAL` секунд. Если Telegram
отвергает rich-черновик (незакрытый Markdown посреди потока), обновления
деградируют до plain-черновика `sendMessageDraft`, а при повторном отказе
просто прекращаются — финальный ответ это не затрагивает.

Стрим не снижает надёжность: HTTP-ошибка, обрыв, «зависание» без данных дольше
`STREAM_STALL_TIMEOUT` секунд — запрос автоматически повторяется обычным
одиночным вызовом. Индикатор «жду ответа» при стриминге исчезает с первым же
куском ответа. Гостевые ответы не стримятся (`answerGuestQuery` поддерживает
ровно один результат). Стримится и анализ фото.

### 📄 Telegraph: таблицы и формулы (fallback)

**По умолчанию выключен** (`TELEGRAPH_ENABLED=false`). При включении полный
ответ становится доступен всем, у кого есть ссылка. Приватный контекст
(документы, прочитанные ссылки, пересланные сообщения, MCP-заметки и анализ
фото) **не публикуется**: такие ответы остаются в Telegram, даже если
`TELEGRAPH_ENABLED=true`. Прокси из переменных окружения Telegraph-сессия не
использует.

Используется при `TELEGRAPH_ENABLED=true`, только когда `RICH_MESSAGES=false` или Telegram отверг
rich-сообщение, и только для ответов без приватного контекста. Если после всех нормализаций
ответ всё ещё содержит Markdown-таблицы и LaTeX (которых нет ни в обычной
подсветке, ни на старых клиентах), `bot/services/telegraph.py` публикует весь
ответ страницей Telegraph, а в чат вместо сломанного текста приходит ссылка с
тем же
временным футером. Telegraph больше **не принимает анонимные `createPage`**
(`ACCESS_TOKEN_INVALID`): страница публикуется от имени аккаунта — либо
заданного в `.env` (`TELEGRAPH_SHORT_NAME` + `TELEGRAPH_ACCESS_TOKEN`, получить
однократным вызовом `createAccount`), либо бот создаёт анонимный аккаунт сам и
сохраняет токен в `TELEGRAPH_ACCOUNT_FILE` (по умолчанию
`/var/lib/kapum-chatbot/telegraph_account.json` — файл с секретом, добавлен
в `.gitignore`; путь обязан быть абсолютным). Если
сохранённый токен отзовут, бот заметит это по ошибке API, создаст новый
аккаунт и повторит публикацию; при недоступности Telegraph срабатывает общий
фолбэк — ответ приходит в Telegram как раньше.

Что считается «неотобразимым» (вне блоков кода и `inline code`):
- таблица — строка `|…|` под которой строка-разделитель `|---|---|` (≥2 колонок);
- LaTeX, который не удалось привести к Unicode: `$E=mc^2$`, `\frac…`, `\begin{…}`;
- блочные `$$…$$` и `\[…\]` **не** считаются при `RENDER_FORMULA_IMAGES=true` —
  они и так уходят в чат PNG-картинками.

Ложные срабатывания исключены: цены («$5 и $10»), Windows-пути (`\Users`),
таблицы внутри ``` — не триггерят. В API Telegraph нет тегов `table` и
`formula`, поэтому на странице таблицы становятся списками (первая колонка
жирным, остальные как `заголовок: значение`), а LaTeX — узлами `code`. Payload
всегда передаётся в поле `content`. Публикация идёт цепочкой деградации: полные
ноды → упрощённые ноды (списки вместо таблиц) → сырой Markdown в p-нодах.
Если Telegraph недоступен целиком — ответ приходит в
Telegram как раньше и ничего не теряется. Проверить доступность прямо с
сервера: `python scripts/check_telegraph.py` — покажет raw-ответы
`createAccount`/`createPage` (токены маскируются) и выдаст готовые строки
`TELEGRAPH_SHORT_NAME`/`TELEGRAPH_ACCESS_TOKEN` для `.env`, если аккаунт
создаётся. Сессия учитывает `HTTPS_PROXY`:
`telegra.ph` блокируется в ряде регионов, поэтому локально фича может не
работать, а на сервере за границей или через прокси — будет.

### 🔀 «Спросить у другой модели»

Под каждым текстовым ответом в **личном чате** — кнопка «🔀 Ask another
model». Она показывает выбор моделей и один раз повторяет последний вопрос
выбранной моделью (callback `resend:<model>`): настройка модели по умолчанию не
меняется, история дополняется как обычным вопросом, квота расходуется. Последний
вопрос чата хранится в памяти (до 500 чатов) — после рестарта бота кнопка
честно просит задать вопрос заново. В группах и в гостевом режиме кнопка не
появляется; на ответы про фото — тоже (повтор требует вложения).

### Почему ответ мог потеряться (и что исправлено)

Ответ исчезал молча в нескольких местах — все закрыты:

| Причина | Было | Стало |
|---------|------|-------|
| Лимит Telegram (429) | `TelegramRetryAfter` **не** наследуется от `TelegramBadRequest`, исключение улетало из `send_formatted` | ждём `retry_after` и повторяем (до 3 раз), затем следующий режим разметки |
| Индикатор + ответ в одну секунду | правка сообщения и отправка ответа сталкивались → 429 | общий троттлинг на чат (~1.05 с между исходящими), им пользуются и индикатор, и ответ |
| Несколько частей длинного ответа | части уходили подряд, часть отклонялась | каждая часть доставляется отдельно, сбой одной не теряет остальные |
| `send_long_message` игнорировал результат | `False` никто не проверял → тишина | проверка результата, запасная отправка простым текстом и явное сообщение об ошибке |
| Любое исключение в обработчике (например, недоступна БД) | aiogram только писал лог, пользователь не получал ничего | глобальный `@dp.error()` пишет лог и отвечает пользователю (в guest mode — закрывает запрос текстом ошибки) |
| Неизвестная команда `/что-то` | не попадала ни в один фильтр → тишина | отдельный обработчик: в личке объясняет и отправляет к /help, в группах — только если команда адресована боту |
| «message is too long» | часть ответа терялась | повтор простой текстовой отправкой с обрезкой до лимита |

Поведение при блокировке бота пользователем (`TelegramForbiddenError`) —
без бессмысленных повторов: одна попытка и лог.

запросы всех пользователей, обработку документов, ссылок и медиа,
генерацию изображений/стикеров, гостевые запросы, дайджесты групп/каналов
(в том числе тестовые), выполняющиеся напоминания и рассылки.
Видны инициатор, чат, этап и длительность; свои операции помечены
`Your task`, у рассылок есть счётчик получателей и ошибок. Доступ — только
владельцу и назначенным админам в личке, с повторной проверкой прав при
обновлении. `Refresh` обновляет страницу, стрелки листают по пять операций.
Содержимое запросов и файлов не показывается, квота не расходуется.
Это снимок текущего процесса: завершённые операции удаляются, после
перезапуска список пустой; будущие напоминания и системные службы сюда не входят.

### 📣 Broadcast

`/broadcast <текст>` (или reply на сообщение с `/broadcast`) отправляет
объявление **всем зарегистрированным пользователям**. Перед отправкой
показывается превью и кнопки «Send» / «Cancel» — случайная рассылка из-за
опечатки исключена. Текст уходит простым (plain) текстом, поэтому сбой
разметки не теряет сообщение; недоступные получатели (заблокировали бота)
просто пропускаются и попадают в счётчик «Failed».

### ❤️ Health endpoint

У Telegram-бота нет собственного HTTP-интерфейса, поэтому для systemd, Docker
или внешнего uptime-монитора можно включить лёгкий эндпоинт:

```
HEALTH_PORT=8080
HEALTH_HOST=127.0.0.1   # по умолчанию loopback, наружу не выставлен
```

`GET /health` отвечает `200 OK` и JSON: `{"status": "ok", "uptime_seconds": …}`.
При `HEALTH_PORT=0` (по умолчанию) сервер не запускается. Если порт занят,
бот продолжает работу — ошибка только логируется.

### ✏️ Правка сообщений

Если пользователь отредактировал уже отправленный вопрос, бот не отвечает
молча: он присылает короткую заметку, что ответ выше был построен на прежней
версии, и предлагает спросить заново (в личке — с кнопкой «🔀 Ask another
model»). Правка **не расходует квоту** и не запускает новый платный запрос
автоматически — иначе исправление опечатки стоило бы вопроса из дневного
лимита. В группах заметка появляется только если сообщение адресовано боту.

## 🌍 Guest chat mode — вызов бота в любом чате

Используется **Guest Mode** из Bot API 10.0 (не inline-режим). Бот получает
отдельный апдейт `guest_message`, когда его упоминают в **любом** чате — группе
или личной переписке с другим человеком, — даже если он туда не добавлен, и
отвечает **от своего имени** прямо в этот чат через `answerGuestQuery`.

**Как включить:**

1. Откройте [@BotFather](https://t.me/BotFather) → Mini App → ваш бот →
   **Bot Settings** → включите **Guest Mode**.
2. В любом чате упомяните бота: `@ваш_бот вопрос` (или ответьте reply на его
   сообщение). Можно упомянуть до 3 guest-ботов в одном сообщении.

**Что умеет guest-режим в этом боте:**

- 💬 текстовый вопрос → ответ с Markdown-разметкой;
- 🎤 голосовое сообщение → распознаётся (`qwen-audio-3.0-realtime-plus`) и
  обрабатывается как обычный текстовый запрос;
- 🖼️ фото в сообщении или в сообщении, на которое отвечают, → анализ
  vision-моделью;
- 🎨 просьба «нарисуй …» → бот отвечает **ссылкой на картинку** без предпросмотра.
  Генератор возвращает временный PNG URL, а `InlineQueryResultPhoto` требует
  доступный серверам Telegram JPEG. В личном чате `/image` отправляет само фото.

**Недоверенный контент.** Документы, OCR, страницы по ссылкам, пересланный текст,
чужое голосовое и фото из reply считаются третьей стороной: текст оборачивается
в `<untrusted_content>` (фото и голос — меткой происхождения), в системный промпт
добавляется `UNTRUSTED_SYSTEM_HINT`, а инструмент генерации картинок не
предлагается. Поэтому чужой текст не может заказать платную генерацию; модель
отвечает текстом. По пересланной подписи фото классификатор `generate`/`enhance`
не запускается. Своё фото или голосовое из собственного сообщения остаются
доверенными.

**Ограничения Telegram:** guest-бот не получает историю чата и список
участников, видит только сообщение-вызов (и сообщение, на которое оно
отвечает), и может дать **ровно один ответ** на вызов. Поэтому вся работа
ограничена таймаутом `GUEST_TIMEOUT`. Выполняется одна попытка отправки:
после отказа гостевой запрос может быть уже недействительным. Локальный
таймаут не продлевает срок действия запроса на стороне Telegram.
Свою историю бот ведёт сам — по
паре `chat_id` и ID пользователя, так что контекст между вызовами сохраняется,
но не смешивается с запросами других участников.

> Inline-режим в боте **отключён и не используется**.

## 👥 Работа в группах

Чтобы бот отвечал в группах:

1. В @BotFather: **Bot Settings → Group Privacy → Turn off** (иначе бот видит

2. Добавьте бота в группу.
3. Упоминайте его (`@ваш_бот ...`) или отвечайте (reply) на его сообщение.

## 🧹 Очистка кэша `__pycache__`

`__pycache__` — это кэш байт-кода Python: он создаётся автоматически и не нужен
при загрузке на хостинг, а старые `.pyc` от удалённых файлов или другой версии
Python могут даже запутать. Удаляется утилитами — безопасно, при следующем
запуске кэш создастся заново. По умолчанию оба скрипта чистят корень проекта
(папку, где лежит сам проект), отключённый режим — показ без удаления:

```powershell
# Windows (PowerShell)
.\scripts\clean_pycache.ps1 -DryRun    # только показать
.\scripts\clean_pycache.ps1            # удалить во всём проекте
# если выполнение скриптов запрещено политикой:
powershell -ExecutionPolicy Bypass -File .\scripts\clean_pycache.ps1
```

```bash
# Linux / macOS (работает и в Git Bash под Windows)
./scripts/clean_pycache.sh -n          # dry-run, только показать
./scripts/clean_pycache.sh             # удалить во всём проекте
./scripts/clean_pycache.sh -p PATH     # очистить другую папку
chmod +x scripts/clean_pycache.sh      # один раз после клонирования на Linux
```

На сервере чистить кэш вручную не нужно: юнит `chat_bot.service` запускает
Python с `PYTHONDONTWRITEBYTECODE=1`, поэтому новые `.pyc` не создаются.
Старые root-owned `__pycache__` удаляет `restart.sh` от root; запускать
`clean_pycache.sh` из юнита от `brain` нельзя — код и кэш принадлежат
`root:root`, и `rm` получает `Permission denied`. Скрипт остаётся ручной
утилитой для обслуживания (запускать от root или на своей копии проекта).

## 🐧 Запуск под systemd (Linux)

Бот работает от отдельного системного пользователя `brain`, код лежит в
`/opt/KapumChatBot` и принадлежит `root:root` (сервис его только читает),
а изменяемые данные — в `/var/lib/kapum-chatbot`, который создаёт systemd
(`StateDirectory=`). Это закрывает главный риск аудита: RCE в боте или в
MCP-сервере больше не даёт root и не позволяет незаметно править код.

```bash
# 1. Системный пользователь без логина и домашнего каталога
sudo useradd --system --user-group --no-create-home --shell /usr/sbin/nologin brain

# 2. Код: владелец root, сервису достаточно чтения
sudo git clone https://github.com/Klajnor/KapumChatBot.git /opt/KapumChatBot
sudo chown -R root:root /opt/KapumChatBot

# 3. Виртуальное окружение — на сервере (не копируйте .venv с Windows)
sudo python3 -m venv /opt/KapumChatBot/.venv
sudo /opt/KapumChatBot/.venv/bin/pip install --upgrade pip
sudo /opt/KapumChatBot/.venv/bin/pip install -r /opt/KapumChatBot/requirements.txt

# 4. Конфиг: из шаблона, затем заполнить BOT_TOKEN, AI_API_KEY, DATABASE_URL, …
sudo cp /opt/KapumChatBot/.env.example /opt/KapumChatBot/.env
sudo nano /opt/KapumChatBot/.env
sudo chown root:brain /opt/KapumChatBot/.env
sudo chmod 640 /opt/KapumChatBot/.env

# 5. Юнит
sudo cp /opt/KapumChatBot/chat_bot.service /etc/systemd/system/chat_bot.service
sudo systemd-analyze verify /etc/systemd/system/chat_bot.service
sudo systemctl daemon-reload
sudo systemctl enable --now chat_bot
sudo journalctl -u chat_bot -f
```

Ошибки и предупреждения дополнительно пишутся в
`/var/lib/kapum-chatbot/errors.log` (`LOG_FILE=auto`, ротация 5 МиБ × 3):
это удобно, когда журнал systemd уже прокручен, а разобраться нужно
постфактум. `journalctl` остаётся полным журналом, включая INFO.

`sudo ./restart.sh` перезапускает сервис и **возвращает** эту схему прав, если
она была нарушена: код и `.venv` — `root:root` без записи для группы,
`.env.linux`/`.env`/`.mcp.json` — `root:brain 640`, БД и токен Telegraph — `brain:brain 600`,
`StateDirectory` — `brain:brain 700`.
Права внутри каталога данных выставляются через открытые дескрипторы
(`scripts/secure_data_permissions.py`, системный `/usr/bin/python3`): символические
ссылки, специальные файлы и файлы с несколькими жёсткими ссылками пропускаются.
Скрипт не делает сервис владельцем кода: иначе RCE в боте или MCP мог бы закрепиться в `/opt/KapumChatBot` до
перезапуска.

Запускайте скрипт как отдельный процесс (`sudo ./restart.sh`), **не** через
`source`/`.`: он меняет `set -e` и не должен переопределять trap/exit
интерактивной оболочки. Ctrl+C останавливает только `journalctl` и возвращает
в консоль, не закрывая SSH-сессию.

На Debian/Ubuntu для шага 3 нужен пакет `python3-venv`; для голосовых
сообщений — `ffmpeg` (см. раздел про установку ffmpeg выше).

В серверном `.env.linux` (или `.env`, если платформенного файла нет) **все
пути обязаны быть абсолютными** (относительные отклоняются при старте).
Пример для каталога данных (обратите внимание на четыре слэша — это
абсолютный путь SQLite):

```env
DATABASE_URL=sqlite+aiosqlite:////var/lib/kapum-chatbot/chat_bot.db
TELEGRAPH_ACCOUNT_FILE=/var/lib/kapum-chatbot/telegraph_account.json
STICKER_MODEL_DIR=/var/lib/kapum-chatbot/rembg
```

Перенос существующей базы — один раз, при остановленном сервисе:

```bash
sudo systemctl stop chat_bot
sudo install -d -o brain -g brain -m 700 /var/lib/kapum-chatbot
sudo install -o brain -g brain -m 600 \
    /путь/к/старому/chat_bot.db /var/lib/kapum-chatbot/chat_bot.db
sudo systemctl start chat_bot
ls -l /var/lib/kapum-chatbot          # владелец brain, файлы -rw-------
```

Что делает юнит:

- `User=brain` / `Group=brain` — никакого root;
- `UMask=0077` — БД, WAL-файлы и `telegraph_account.json` создаются с правами
  `0600`, а не `0644`;
- `StateDirectory=kapum-chatbot` / `CacheDirectory=kapum-chatbot` — каталоги
  данных и кэша matplotlib создаются с нужным владельцем автоматически;
- `U2NET_HOME=/var/lib/kapum-chatbot/rembg` — запасной путь к модели, если
  `STICKER_MODEL_DIR` не задан в `.env` (значение абсолютное);
- `PYTHONDONTWRITEBYTECODE=1` — `.pyc` не пишутся, поэтому код может быть
  read-only, а предзапусковая очистка кэша не нужна;
- `RestartSec=5s` — при ошибке конфигурации нет шторма рестартов;
- `ProtectHome`, `PrivateDevices`, `ProtectKernel*`, `RestrictAddressFamilies`,
  `RestrictNamespaces`, `LockPersonality`, пустой `CapabilityBoundingSet` —
  стандартный набор ограничений для сетевого сервиса без локальных устройств.

Если хранилище Obsidian для MCP находится в `/home`, замените
`ProtectHome=true` на `ProtectHome=false` (или явно откройте каталог через
`ReadOnlyPaths=`), иначе MCP-сервер его не увидит. `MemoryDenyWriteExecute` и
`SystemCallFilter` в юнит намеренно не добавлены: они ломают часть
C-расширений (numpy/matplotlib/Pillow) — включайте только после проверки.

### 🔄 Автообновление на сервере (systemd timer)

`scripts/update.sh` и `kapum-update.timer` раз в ~10 минут сверяют `HEAD` в
`/opt/KapumChatBot` **и** в `/opt/brain` (ObsidianBrain, если установлен) с
их `origin/master`. Проверка запускается через 10 минут **после завершения**
предыдущей (плюс случайный сдвиг до двух минут). Обновление выполняется от
root, а бот и MCP работают от `brain` и не получают права менять код.

Поддерживается только **fast-forward**: локальные коммиты, изменённые tracked-
файлы, конфликты с untracked-файлами или попытка затронуть `.env*` (кроме
`.env.example`), `.venv`, `.mcp.json`, `data/` и базы отменяют обновление
этого репозитория. Сбой ключа одного клона не мешает обновлению другого.
Во время замены кода бот остановлен: живые процессы не смешивают старые и
новые Python-модули. После изменения **любого** клона бот перезапускается,
поэтому его stdio MCP-процесс тоже получает новый код.

Перед включением проверьте владельцев: оба каталога кода, `.git`, `.venv` и
конфиги должны принадлежать root и не быть доступны `brain` на запись.
Обновлятор **откажется** исполнять root-команды над кодом, изменяемым сервисом.
У мозга только `/opt/brain/data` остаётся `brain:brain` (каталог `700`, файлы
`600`), `.env` — `root:brain 640`; для его Python нужен
`/opt/brain/.venv/bin/python3`. Код/окружения должны читаться пользователем
`brain`. Обновлятор не исправляет небезопасные права мозга автоматически —
сначала вручную проверьте содержимое клона и приведите права к этой схеме.

Репозитории закрытые, поэтому серверу нужны отдельные read-only deploy-ключи
**без парольной фразы** (пароль в автоматике вводить некому). Каждый ключ
привязан к своему репозиторию (GitHub не допускает один deploy-ключ в двух
репозиториях) и может только читать; ключи с фразой из `load_git_key.sh`
остаются для ручных сессий.

```bash
# 1. Deploy-ключи (на сервере); публичные части добавить в GitHub:
#    репозиторий → Settings → Deploy keys → Add deploy key.
#    Галку «Allow write access» НЕ включать.
sudo ssh-keygen -t ed25519 -f /root/id_ed25519_kapum_deploy -N "" -C "kapum-server-deploy"
sudo cat /root/id_ed25519_kapum_deploy.pub
sudo ssh-keygen -t ed25519 -f /root/id_ed25519_brain_deploy -N "" -C "brain-server-deploy"
sudo cat /root/id_ed25519_brain_deploy.pub   # в репозиторий ObsidianBrain

# 2. origin переключить на SSH (клоны по инструкции выше сделаны по HTTPS)
sudo git -C /opt/KapumChatBot remote set-url origin git@github.com:Klajnor/KapumChatBot.git
sudo git -C /opt/brain remote set-url origin git@github.com:Klajnor/ObsidianBrain.git

# 3. Проверить fingerprint GitHub по официальной документации и подтвердить
#    host key в /root/.ssh/known_hosts (не использовать слепой ssh-keyscan).
#    GitHub при успешной аутентификации сообщает «successfully authenticated»,
#    но ssh -T завершается с кодом 1: shell-доступ не предоставляется.
sudo ssh -F /dev/null -i /root/id_ed25519_kapum_deploy -o IdentitiesOnly=yes -o IdentityAgent=none -T git@github.com
sudo ssh -F /dev/null -i /root/id_ed25519_brain_deploy -o IdentitiesOnly=yes -o IdentityAgent=none -T git@github.com

# 4. Юниты таймера; сначала вручную проверить обновление, затем включить опрос.
sudo cp /opt/KapumChatBot/kapum-update.service /opt/KapumChatBot/kapum-update.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start kapum-update.service       # первая проверка вручную
sudo journalctl -u kapum-update -n 50 --no-pager
sudo systemctl enable --now kapum-update.timer
systemctl list-timers kapum-update.timer        # следующее срабатывание
```

Если `/opt/brain` на сервере нет, скрипт молча обновляет только бота. Для
проверки готовности включите `HEALTH_PORT` в серверном `.env.linux`
(эндпоинт слушает `127.0.0.1` и наружу не виден); уведомления используют
`BOT_TOKEN` и `OWNER_IDS` из того же файла. Откат и уведомления работают и
без порта — тогда готовность проверяется активностью юнита без роста
автоперезапусков.

Проверки и восстановление:

- `flock` исключает параллельные запуски. Состояние каждого клона хранится
  в `/var/lib/kapum-update/{bot,brain}.state` и переживает перезагрузку:
  об одной блокировке сообщается один раз, откатившийся SHA не пробуется до
  нового коммита. Для ручного повтора исправленной конфигурации удалите только
  соответствующий `.state` при остановленном обновляторе.
- Git работает без хуков, с `BatchMode=yes`, проверенным host key и одним
  deploy-ключом. Fetch и pip имеют таймауты; секреты не передаются в argv.
- Если изменился `requirements.txt`, сначала сохраняется полная копия `.venv`
  в `/var/lib/kapum-update/backup.*` (reflink или обычное копирование): нужен
  свободный диск под оба окружения. Снимки не занимают tmpfs `/run`.
  Установка выполняется только в соответствующий venv, не в системный Python.
- Активный `brain-sync.service` останавливается и восстанавливается после.
  Если `brain-pull.service` уже индексирует хранилища, обновление мозга просто
  пропускается до следующего запуска обновлятора: прогон не прерывается,
  таймер не останавливается, коммит не помечается неудачным. Обновление самого
  бота независимо и может продолжиться. Повторная проверка после приостановки
  таймера защищает от прогона, начавшегося одновременно с обновлением.
- `ast.parse` проверяет код без выполнения и `.pyc`. После рестарта мозг
  дополнительно проходит настоящий MCP `initialize`/`tools/list` **от brain**,
  без LLM, чтения БД и инструментов записи. Один `/health` бота эту проверку
  не заменяет: MCP запускается лениво.
- Бот (и ранее активный watch-индексатор) должны 20 секунд оставаться активными
  без смены PID и `NRestarts`; при включённом health нужен JSON `status=ok`.
  На готовность даётся до 60 секунд.
- Ошибка → откат только затронутых коммитов и восстановление снимков `.venv`,
  затем повторные проверки. При неполном откате копии сохраняются в указанном
  в уведомлении `/var/lib/kapum-update/backup.*`. Эти снимки сохраняются и при
  перезагрузке.
- **`brain-pull.timer` возвращается при любом исходе**: успехе, ошибке,
  прерывании и даже неполном откате. Восстанавливается ранее активный или
  включённый (`enabled`), но остановленный таймер; намеренно отключённый
  (`disabled` и неактивный) не включается. Если systemd не смог запустить
  таймер, обновлятор завершается с ошибкой и сообщает об этом отдельно в
  итоговом уведомлении. После неполного отката проверьте диагностику —
  расписание продолжится, но причина сбоя всё ещё требует исправления.
- Уведомления об успехе, блокировке и откате отправляются владельцам в Telegram;
  конфиг читается как у бота: **один** `.env.linux`, иначе `.env`, с приоритетом
  окружения. `.env` не исполняется как shell-скрипт.
- При неудаче уведомление содержит коммиты, этап и код выхода, безопасную
  причину, результат отката с перечнем неудавшихся шагов, состояние таймера и
  служб (`ActiveState`, `Result`, `ExecMainStatus`, `NRestarts`), путь к
  сохранённым копиям и команду просмотра журнала. Синтаксическая ошибка
  показывает файл/строку, ошибка прав — путь/UID/режим, MCP — фазу handshake
  и категорию ошибки (например, отсутствующий модуль). Сырой stderr MCP,
  исходный текст, заметки и значения секретов в Telegram не пересылаются.

**Ограничения:** заметки, БД и миграции данных не откатываются; автоматически
обновляйте только обратно совместимые изменения, перед миграциями делайте
отдельный backup SQLite. Системные пакеты и установленные systemd-юниты не
заменяются (в них могут быть локальные пути/настройки). Защитите `master` в
GitHub: это доверенный источник кода, который обновлятор устанавливает от root.

#### Если обновление brain заблокировано из-за прав

Сообщение `code must be root-owned and not writable by the service` означает,
что код, `.git`, `.venv` или конфиги в `/opt/brain` принадлежат не root либо
доступны группе/остальным на запись. Проверяются также родительские каталоги
и цели символических ссылок.

Сначала убедитесь, что это ваша доверенная копия кода. Затем, без параллельного
запуска обновлятора, исправьте права:

```bash
# Код — root; каталог data полностью пропускается
sudo find /opt/brain -path /opt/brain/data -prune -o \
  -exec chown -h root:root -- {} +

sudo find /opt/brain -path /opt/brain/data -prune -o \
  \( -type d -o -type f \) -exec chmod go-w -- {} +

# Конфиг должен оставаться доступен сервису на чтение
sudo chown root:brain /opt/brain/.env
sudo chmod 640 /opt/brain/.env

# Повторить обновление и посмотреть результат
sudo systemctl start kapum-update.service
sudo journalctl -u kapum-update -n 30 --no-pager
```

**`/opt/brain/data` оставьте владельцу `brain`**: там изменяемый индекс.
Команды выше не меняют его содержимое, владельцев и права. Код и `.venv`
должны по-прежнему читаться пользователем `brain`; права чтения/исполнения
эти команды не добавляют.

Если блокировка осталась, проверьте `ls -ld / /opt /opt/brain` и цели ссылок
внутри `.venv`: они тоже должны принадлежать root и не быть доступны группе
или остальным на запись. При этой блокировке удалять `brain.state` не нужно:
при следующем запуске обновлятор проверит исправленные права заново.

## 🗄️ База данных

Сейчас поддерживается **только SQLite**: один файл в каталоге данных
(`/var/lib/kapum-chatbot/chat_bot.db` в `.env.example` и в systemd-разделе
выше; относительные пути запрещены).
WAL и busy_timeout включаются автоматически, таблицы создаются при старте бота.
Резервная копия — просто скопировать файл при остановленном сервисе.

PostgreSQL и другие СУБД — **возможное будущее направление**. Исторический
`asyncpg` и ветки диалектов остаются в коде как задел, но не поддерживаются,
не тестируются и не документируются как рабочий вариант. Скрипт переноса
`migrate_to_sqlite.py` удалён: при возврате к PostgreSQL его нужно писать
заново и покрывать тестом на все таблицы (напоминания, настройки, дайджест,
стикеры, intent-бюджеты), иначе данные потеряются.

## Логи запросов к AI API

По умолчанию на уровне `INFO` логируются только метаданные: модель, параметры
запроса, число сообщений и их длина (без текста), метаданные медиа (тип, MIME,
размер), имена инструментов, попытки отправки, HTTP-статус и время ответа.
Общий `id` связывает записи одного запроса. Тексты переписки, история, запросы
поиска, аргументы и результаты инструментов в лог **не попадают** — журнал не
должен превращаться в архив личных разговоров.

Для отладки можно включить полные тексты: `LOG_PROMPTS=true` — тогда они
пишутся на уровне `DEBUG` (логгер `bot.services.ai_client` автоматически
переводится в DEBUG, остальные библиотеки остаются на INFO; при старте
выводится предупреждение). Держите такие логи приватными и выключайте опцию
после отладки. API-ключи и временные ссылки на медиа не включаются в запись
исходящего запроса ни в каком режиме.

Отдельный ротируемый журнал ошибок включается через `LOG_FILE` (по умолчанию
`auto` — файл `errors.log` рядом с SQLite-базой, то есть в каталоге, куда
сервис и так пишет). В него попадают записи уровня `LOG_FILE_LEVEL`
(по умолчанию `WARNING`) и выше: необработанные исключения с traceback,
сбои Telegram/API и отказы поиска с кодом причины (`timeout`, `http_401`,
`invalid_json`, `network`), номером операции, чатом и пользователем. Запрос
поиска, сниппеты и прочитанные страницы в журнал не пишутся. Ротация — 5 МиБ,
хранится 3 архивных файла; `LOG_FILE=off` оставляет только journald/stdout.
На systemd файл находится в `/var/lib/kapum-chatbot/errors.log`.

Если провайдер поиска не ответил, бот не выдаёт это за «ничего не найдено»:
в личном чате он пишет, что поиск сейчас недоступен, а запрос повторяется
без инструмента `search_web` — ответ строится на знаниях модели. Сбой
фиксируется в журнале ошибок с причиной и идентификаторами запроса.

## Формулы в виде картинок

`RENDER_FORMULA_IMAGES=true` включает отрисовку через Matplotlib MathText без
установки LaTeX и без внешних сервисов. После обновления установите зависимости:
`python -m pip install -r requirements.txt`.

Модель получает инструкцию выделять сложные формулы через `\[...\]`.
Поддерживаются также `$$...$$`. Например:

```text
Корни квадратного уравнения:
\[x = \frac{-b \pm \sqrt{b^2 - 4ac}}{2a}\]
```

Бот отправляет пояснение текстом, а формулу — отдельной картинкой на белом фоне.
Короткая математика в строке преобразуется в Unicode при `NORMALIZE_FORMULAS=true`.
Исходная запись сохраняется в истории; код не обрабатывается как формулы.
Используется ограниченное подмножество TeX: окружения `align`, `matrix`, пакеты
и пользовательские команды могут не поддерживаться и отправляются текстом.
В ответе обрабатывается не более шести формул для PNG, остальные остаются текстом;
есть ограничения длины выражения и размеров изображения. Рендер выполняется вне
цикла обработки сообщений, повторные формулы кешируются.

В гостевом режиме используется Unicode: локальные PNG нельзя прикрепить к
единственному результату гостевого ответа без предварительной загрузки на сервер.
`RENDER_FORMULA_IMAGES=false` возвращает прежний текстовый режим.
Пользовательский `STYLE_HINT` сохраняет приоритет над встроенной инструкцией.

## 🔄 Переход с OpenRouter

Старый клиент OpenRouter заменён на универсальный OpenAI-совместимый клиент
`bot/services/ai_client.py`. Достаточно указать ключ и `AI_BASE_URL` Qwen —
код, форматы запросов и ответов совпадают.
